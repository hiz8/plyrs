# 案 C: 編集画面の公開ボックス 設計

[現状構造の棚卸し](./current-structure.md) の案 C(2026-10-17 採用)を具体化する。対象はコンテンツの作成画面と編集画面(現 `routes/t/$tenantSlug/records/$typeKey/new.tsx` と `$recordId.tsx`)。呼称は棚卸し 6.1 の決定に従う(「レコード」は使わず型名で呼ぶ)。

## 1. 目的

WordPress の「公開」ボックスに慣れた利用者が、保存と公開の関係を迷わず扱えるようにする。現状は保存・公開・ステータス・公開状態・削除が 4 か所に分かれ、「公開」は保存済みの版しか公開しないため、未保存の編集が公開に含まれない。

## 2. 画面構成

```
┌──────────────────────────────────────┬──────────────────────────┐
│ お知らせを編集                          │ 公開                      │
│                                      │  状態      [● 公開中]        │
│ [フィールド入力 …]                     │           2026/10/17 10:00 に公開 │
│                                      │           ● 未反映の変更があります │
│                                      │           ✎ 未保存の変更があります │
│                                      │  ステータス [下書き ▾]        │
│                                      │                          │
│                                      │       [公開せずに保存] [更新] │
│                                      │                  公開を取り下げ │
│                                      │  ─────────────            │
│                                      │  削除                     │
│                                      ├──────────────────────────┤
│                                      │ (モジュールのパネル …)        │
└──────────────────────────────────────┴──────────────────────────┘
```

- 右サイドバー最上段に「公開」ボックスを置き、保存・公開・ステータス・公開状態・削除をここに集約する
- 本文下の「保存」ボタン、上部ツールバーの「公開」「公開を取り下げ」、最下部の「削除」は廃止する
- 公開ボックスの下に、既存の `record-editor:panel` スロットのパネルを並べる
- 狭い画面(幅 960px 未満)ではボックスをフォームの後ろ(下)に回し、画面下部に固定したバーに主ボタンと補助ボタン、未反映 / 未保存の注記を置く。取り下げ・削除・ステータスはボックス側だけ(D2 で確定)
- ボックスの見た目(D2 で確定): `bg.surface` のカード(`radius.container`)、題「公開」16px 600。状態は公開状態のバッジ(公開中 / 未公開、新規は「まだ保存されていません」)と公開日時。ステータスは 28px のセレクト。ボタンは右寄せで主ボタンが右端、補助ボタンがその左。「公開を取り下げ」はボタンの下に右寄せの危険色テキストリンク、「削除」は罫線で区切った最下部の危険色テキストリンク
- 本文の右列は幅 300px、フォームとの間隔 32px。右列は公開ボックス → モジュールのパネルの順で、スクロールに追従しない
- 見出しの右には主操作を置かず、「最終更新 10 分前 ・ editor@example.com」を添える
- (2026-10-20、V3)見出しの右の補足は「最終更新 10 分前」(相対表記 + ツールチップ)だけにする。`updatedBy` はユーザー ID で、メールへの解決は案 G のメンバー情報の取得方法が決まってから(D 10 章の「最終更新者の列」と同じ扱い)。閲覧者は錠アイコン +「閲覧のみ ・ 最終更新 10 分前」(R1)
- (2026-10-20、V3)見出しは `{型名}を編集` とする(D2 E2 のタイトル表示は採らない)。閲覧者は `{型名}を表示`(R12)

## 3. ボタンと状態

公開状態(`published_snapshots` の有無、design-spec §7)と未反映の変更の有無で、ボタンの組み合わせを切り替える。

| 状態                                                       | 主ボタン   | 補助ボタン     | 追加の操作           |
| ---------------------------------------------------------- | ---------- | -------------- | -------------------- |
| 新規作成(未保存)                                           | 公開       | 下書き保存     | —                    |
| 未公開                                                     | 公開       | 下書き保存     | 削除                 |
| 公開中・未反映の変更なし・フォームも未編集                 | 更新(無効) | —              | 公開を取り下げ、削除 |
| 公開中・未反映の変更あり、またはフォームに未保存の編集あり | 更新       | 公開せずに保存 | 公開を取り下げ、削除 |

- **公開 / 更新**: フォームに未保存の編集があれば保存し、保存の確定を待ってから公開する(3 章参照)
- **下書き保存 / 公開せずに保存**: 保存だけを行う。公開中のコンテンツでは公開版は変わらず、「未反映の変更があります」が表示される
- 「未反映の変更あり」は現行の公開状態パネルと同じ判定(`record.version > publication.sourceVersion`)を使う
- 補助ボタンの呼び方は、未公開なら「下書き保存」、公開中なら「公開せずに保存」とする。公開中のものを「下書き保存」と呼ぶと、公開が取り下げられると誤解されやすいため
- 注記の出し分け(D2 で確定): 「未反映の変更があります」は保存済みだが公開版に無い差分で、`status.warning` の点 + 文字。「未保存の変更があります」はこの端末にしかない差分で、鉛筆アイコン + `text.default` の文字。両方あるときは上下に重ねて出す
- (2026-10-20、V3)「更新」が無効のとき(公開中・未反映なし・未編集)は理由のツールチップを付けず `isDisabled` だけにする。この表に理由が無いため。切断中だけ `disabledReason` を付ける(R21)

## 4. 保存してから公開する流れ

API の変更は不要で、管理画面側で次の順に実行する。公開処理(`apps/api/src/do/publish.ts` の `publishRecordCore`)は DO に保存済みのレコードを公開するため、保存の確定を待てば編集内容が公開に含まれる。

1. フォームを検証する。エラーがあれば中断し、該当フィールドへスクロールする
2. 未保存の編集があれば同期経路で保存し、`tx.isPersisted` の確定を待つ
3. `POST /:tenantId/records/:recordId/publish` を呼ぶ
4. 公開状態を再取得し、トーストで「公開しました」「更新しました」と知らせる

失敗時の扱い:

| 失敗した段階        | 表示                                                   | その後                                               |
| ------------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| 1. 検証             | フィールドのエラー                                     | 何も保存・公開しない                                 |
| 2. 保存(本文の競合) | 競合ダイアログ(本章後段)                                   | 公開は行わない。競合を解決したら利用者がもう一度押す |
| 2. 保存(その他)     | 「保存できませんでした」                               | 公開は行わない                                       |
| 3. 公開             | 「保存しましたが、公開できませんでした」+ 再試行ボタン | 保存は確定済みなので、再試行は公開だけを行う         |
| 公開状態の取得      | (2026-10-20、V4-B)公開ボックスの「状態」にエラー文「公開状態を取得できませんでした」と再試行(B16) | 公開の主ボタンは読み込み中と同じく無効。ステータスの変更と削除はできる |

同期が切断中(`ConnectionBanner` が出ている状態)は保存が確定しないため、「公開 / 更新」は無効にし、ボタンの下に「接続が回復すると公開できます。「公開せずに保存」はこの端末に保存され、再接続後に送信されます」と添える(無効なボタンのツールチップにも同じ理由)。「下書き保存」は今と同じくオフラインでも受け付ける(保存は接続回復後に確定する)。

公開に失敗したときのトーストは `role="alert"` のエラー色で「保存しましたが、公開できませんでした。接続を確認して、もう一度お試しください」と「公開を再試行」ボタンを置く(D2 で確定)。本文の競合ダイアログは、相手のメールと保存時刻を示し、自分の編集と相手の編集を左右に並べて差分を強調し、「あなたの編集を残す」(主)と「あとで決める」を置く。他のフィールドは自動で統合済みであること、公開はまだ行っていないことを説明文に書く。

(2026-10-20、V3)切断中の注記は補助ボタンの名前を文に埋め込む。未公開・新規は「「下書き保存」は…」、公開中は「「公開せずに保存」は…」、補助ボタンが無いときは「接続が回復すると公開できます」だけ(D2 E6 の変種、R9)。

(2026-10-20、V3)競合ダイアログは `ModalDialog` で作る。題は「本文が他の人の編集と重なりました」。相手のメールは出せないため「ほかの人が {相対時刻} に同じ本文を保存しました」とする。D2 のラジオ(どちらを残すか)の代わりにボタンを 3 つ置く: 「あなたの編集を残す」(主)、「ほかの人の編集を取り込む」(枠線。現行の「サーバー版を採用」)、「あとで決める」(枠線)。差分の強調(`<mark>`)は入れず、抜粋を並べる(R10)。

## 5. ステータス(ワークフロー状態)

- ボックス内に「ステータス: 下書き [変更]」として表示し、「変更」でセレクトを開く。値は現行どおり 下書き / レビュー中 / 公開準備完了 / アーカイブ
- (2026-10-20、V3)上の「[変更]」は 2 章の「28px のセレクト」に揃える。「変更」リンクは置かず、28px の `Select`(ラベルは部品の標準どおり上に「ステータス」)がそのまま切り替えになる(R6)
- 公開とステータスは独立のまま扱う(design-spec §7 の分離を維持)。公開してもステータスは自動で変わらず、ステータスを変えても公開されない
- 公開中にアーカイブを選んだときの警告(先に公開の取り下げを推奨)は現行の動作を引き継ぐ
- ステータス変更は即時保存のまま(フォームの保存とは独立)

## 6. 作成画面

- 作成画面も編集画面と同じレイアウトと公開ボックスを使う
- 初回の保存(下書き保存・公開のどちらでも)が確定したら、編集画面の URL に置き換える(`navigate({ replace: true })`)。一覧には戻らない
- 作成画面の「公開」は、作成 → 確定待ち → 公開 の順で行う
- (2026-10-20、V3)作成画面の「公開」の順序: 作成(insert の ack 待ち)→ 公開 → トースト → 編集画面の URL へ置き換え(`replace: true, ignoreBlocker: true`)。公開に失敗しても URL は置き換え、エラーのトーストの「公開を再試行」は保存済みの ID に対して公開 API を呼ぶ閉包にする(フックの `retryPublish` はルートをまたぐと使えない)(R22)

## 7. フィードバックと離脱防止

- 保存・公開・取り下げ・削除の結果はトーストで知らせる。トースト部品は `packages/ui` に新設する(現状は無い)
- フォームに未保存の編集がある状態で画面を離れようとしたら確認する。アプリ内の遷移は TanStack Router の `useBlocker`、タブを閉じる・再読み込みは `beforeunload` で扱う。ダイアログは「保存していない変更があります」「このまま移動すると、本文とタイトルの変更は失われます」で、主ボタンは「編集を続ける」、補助は危険色の文字の「破棄して移動」(D2 で確定)
- 未保存の編集があることを、ボックス内に「未保存の変更があります」と表示する
- (2026-10-20、V3)新規作成(未保存)では「未保存の変更があります」を出さない。状態の「まだ保存されていません」で足りる(D2 E1、R7)
- (2026-10-20、V3)離脱確認のダイアログは `ConfirmDialog` ではなく `ModalDialog` + フッターで組む。「破棄して移動」は `Button variant="dangerLink"`、「編集を続ける」は主ボタンで初期フォーカスとする(危険でない確認は実行ボタンにフォーカス、H 8 章)(R11)

## 8. 削除と公開の取り下げ

- 「削除」はボックス最下部のテキストリンクとし、確認ダイアログを経て削除する。公開中のものを削除すると公開も停止される(削除は `cascadeUnpublish` を伴う、`apps/api/src/tenant-do.ts`)ため、ダイアログに警告色の注記「このお知らせは公開中です。削除するとサイトからも消え、公開ページは表示できなくなります」を置く(D2 で確定)
- 「公開を取り下げ」は公開中のときだけ表示し、確認ダイアログを経て実行する
- 確認ダイアログは案 H の共通部品(モーダル)を使う

## 9. 権限

- viewer にはボタンを表示せず、公開状態とステータスの表示だけを残す。フォームは入力欄の枠を外した読み取り専用の表示(下線だけ)にし、本文のツールバーは出さない。パンくずは「編集」ではなく「表示」(D2 で確定)
- (2026-10-20、V3)閲覧者の公開ボックスには、公開日時と「未反映の変更があります」も公開状態の一部として出す(D2 E7)。ステータスは文字だけ(R8)。見出しは `{型名}を表示`、パンくずの現在地は「編集」ではなく「表示」(上の D2 の確定と同じ。R12)
- editor と owner は現行どおりすべての操作ができる(ロールの細分化は design-spec §11.3 の「型 × 操作」権限の実装時に再訪する)

## 10. メディア(asset 型)の編集

- メディアの編集は案 F で専用 UI に移すため、汎用の公開ボックスは出さない
- 案 F が入るまでの間は、メディアの編集画面では公開ボックスから公開関連の操作を外し、「保存」と「削除」だけを表示する。メディアは参照元のコンテンツの公開時に一緒に公開されるため(`publishRecordCore` 内のカスケード)、利用者が個別に公開する必要はない
- (2026-10-20、V3)メディア(asset 型)の編集画面のパンくずは ホーム › メディア › 編集(R12)

## 11. スロットへの影響

- 現在 `record-editor:toolbar` に登録されているコアの `core.publish` と `core.status` は公開ボックスへ移し、スロット登録をやめる。公開ボックス自体はコアの部品とし、スロットにはしない
- `core.publication`(公開状態パネル)は公開ボックスに統合して登録をやめる
- `record-editor:toolbar` と `record-editor:panel` はモジュール用に残す。ツールバーはフォーム上部、パネルは公開ボックスの下に描画する

## 12. 未決事項

- 公開日時の予約(WordPress の「予約投稿」)を公開ボックスに入れるか。DO alarm(design-spec §9.6)で実現できる見込みだが、API の追加が必要
- プレビュー(公開前の見た目の確認)をどう提供するか。公開側の表示はヘッドレスで plyrs の外にあるため、プレビュー URL の設計が別途必要
- 削除をゴミ箱(復元可能)にするか。records には `deletedAt` があるが、復元の手段は無い
