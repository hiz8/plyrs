# 案 G: サイト設定とアカウント 設計

[現状構造の棚卸し](./current-structure.md) の案 G(2026-10-17 採用)を具体化する。対象は [案 A](./a-navigation.md) のサイドバー下段にある「設定」(owner のみ)と「アカウントメニュー」から開く画面。設定のうち「コンテンツタイプ」は [案 E](./e-content-type-design.md) で設計済みのため、本書では「一般」「メンバー」「モジュール」とアカウントを扱う。

## 1. 目的

- テナントの owner が、運営者に頼まずに自分のサイトのメンバーを追加・変更できるようにする(WordPress の「ユーザー」に相当)。現状、メンバーの管理は運営コンソール(`/super/tenants/:id`)にしか無い
- 公開 API の URL など、サイトの基本情報を確認できる場所を用意する(WordPress の「設定 › 一般」に相当)
- 利用者が自分のアカウント(パスワードなど)を管理できるようにする

## 2. 現状の前提

| 項目                 | 現状                                                                   | 出典                                            |
| -------------------- | ---------------------------------------------------------------------- | ----------------------------------------------- |
| テナントの情報       | 名前と slug のみ                                                       | `packages/db/src/control-plane.ts` の `tenants` |
| テナント名の変更     | 運営者のみ可能                                                         | `apps/api/src/routes/super.ts`(`tenant.rename`) |
| slug の変更          | 不可(公開版に埋め込まれた URL が壊れるため)                            | 同上のコメント(§14-3)                           |
| メンバー             | ユーザー・テナント・ロールの組(`memberships`)                          | `control-plane.ts`                              |
| メンバーの追加       | 運営者がテナント作成時に、登録済みユーザーを owner に任命するのみ      | `super.ts` の `ownerEmail`                      |
| メンバーの剥奪       | 運営者のみ。剥奪後は KV のブロックリストで既存のトークンも即時に無効化 | `apps/api/src/auth/ban.ts`、`blocklist.ts`      |
| ロールの反映         | JWT に `role` を載せる。トークンの有効期間は 15 分                     | design-spec §11.4、`apps/api/src/auth/jwt.ts`   |
| メール送信           | 仕組みが無い(招待メール・パスワード再設定メールは送れない)             | API 全体に送信処理なし                          |
| 自分の情報を返す API | テナント利用者向けには無い                                             | [案 B](./b-home.md) 3 章で追加を予定            |

## 3. 設定 › 一般

```
┌──────────────────────────────────────────────────────────┐
│ 設定 › 一般                                                │
│ 一般                                                       │
│                                                          │
│ サイト名      [plyrs のお店          ]  [保存]               │
│ サイトの識別子  shop-example(変更できません)                   │
│                                                          │
│ 公開 API                                                   │
│  ベース URL   https://…/public/v1/shop-example/  [コピー]     │
│  例: お知らせの一覧  …/records/news                [コピー]     │
└──────────────────────────────────────────────────────────┘
```

- **サイト名**: owner が変更できるようにする。運営者用の変更 API とは別に、テナント利用者向けの変更 API を追加する(owner のみ、監査ログに記録)
- **サイトの識別子(slug)**: 表示のみ。公開 API の URL に含まれ、公開版に埋め込まれた URL が壊れるため変更できない旨を補足に書く
- **公開 API**: ベース URL と、型ごとの一覧の URL の例を表示し、コピーできるようにする。フロントエンドの開発者に URL を伝えるときに使う

## 4. 設定 › メンバー

```
┌──────────────────────────────────────────────────────────┐
│ 設定 › メンバー                                             │
│ メンバー                                     [メンバーを追加]  │
│                                                          │
│ メールアドレス           ロール         参加日      操作        │
│ owner@example.com      管理者(自分)  2026/07/16   —        │
│ editor@example.com     [編集者 ▾]      2026/09/01   [外す]    │
│ viewer@example.com     [閲覧者 ▾]      2026/10/01   [外す]    │
└──────────────────────────────────────────────────────────┘
```

### 4.1 一覧

- 列はメールアドレス・ロール・参加日・操作。ロール名は日本語で表示する(管理者 / 編集者 / 閲覧者)
- 各ロールでできることを、一覧の上に短く説明する(例: 「編集者: コンテンツとメディアの作成・編集・公開ができます。設定は変更できません」)。説明は `apps/api/src/auth/permissions.ts` の権限表に合わせる

### 4.2 メンバーの追加

- 「メンバーを追加」でダイアログを開き、メールアドレスとロールを入力する
- 追加できるのは、plyrs に登録済みのユーザーに限る。メール送信の仕組みが無く、招待メールを送れないため
- 未登録のメールアドレスの場合は「このメールアドレスのユーザーは登録されていません。先にサインアップを依頼してください」と表示し、サインアップ画面の URL をコピーできるようにする
- 登録済みかどうかが owner に分かることになる。owner はテナントの管理者で、追加しようとしている相手のメールアドレスを既に知っている前提のため、許容する(運営者の任命 API と同じ挙動)
- メール送信の仕組みは今回導入しない(9 章)。導入する場合は、招待リンクを送る方式に切り替える

### 4.3 ロールの変更

- 一覧のロール欄から変更する
- 変更はトークンの再発行時に反映されるため、最大 15 分かかる。ロールを下げたとき(編集者 → 閲覧者など)は、ダイアログで「反映まで最大 15 分かかります。すぐに止めたい場合は、いったんメンバーから外してください」と案内する

### 4.4 メンバーを外す

- 確認ダイアログを経て外す。運営者の剥奪と同じく、ブロックリストで既存のトークンも即時に無効化する
- 外したメンバーが作成・編集したコンテンツは残る

### 4.5 owner を失わないための制限

- 最後の owner は、外すこともロールを下げることもできない。テナントを管理できる人がいなくなるのを防ぐため
- 自分自身を外す・ロールを下げる操作は、確認ダイアログで「この操作のあと、設定を開けなくなります」と明示する

### 4.6 必要な API

- メンバー一覧・追加・ロール変更・外す、の 4 つを、テナント利用者向け(owner のみ)に追加する。運営者用の API(`/super/v1/tenants/:tenantId/members`)とは分け、権限判定は既存の認可の仕組み(design-spec §11.5)に乗せる
- 権限は `permissions.ts` に新しい操作(例: `member:manage`)を足し、owner のみに許可する
- 追加・ロール変更・外す操作は監査ログに記録する

## 5. 設定 › モジュール

- 現在の「モジュール」画面(有効化 / 無効化の一覧)をここへ移す
- 各モジュールに説明文と、有効化すると増えるもの(例: 「サイドバーに『予約』が追加されます」「予約・予約枠・予約リソースを管理できます」)を表示する。説明文はモジュールの定義(manifest)に項目を足して持たせる(現在の `BOOKING_MANIFEST` は名前のみ)
- 有効化した直後に、増えた画面へのリンクを表示する
- 無効化するときは、確認ダイアログで「モジュールのコンテンツは削除されません。再び有効化すると元に戻ります」と明示する(推測: 無効化でデータが消えない前提。実装時に確認する)
- 権限不足時の「操作に失敗しました(権限を確認してください)」は、設定自体を owner にしか表示しない(案 A)ことで起きなくなる

## 6. アカウント

アカウントメニュー(サイドバー最下部)から開く。内容はテナントをまたいだ利用者自身の情報だが、画面は現在のテナントのシェルの中に表示する(URL は `/t/:slug/account`)。サイドバーを残したまま確認・変更できるようにするため。

### 6.1 アカウントメニュー

- メールアドレス(表示のみ)
- アカウント設定(6.2 へ)
- サイト切替(所属が複数のとき)
- ログアウト

### 6.2 アカウント設定

- **メールアドレス**: 表示のみ。変更は確認メールが必要になるため、メール送信の仕組みが入るまで設けない
- **パスワードの変更**: 現在のパスワードと新しいパスワード(12 文字以上、サインアップと同じ条件)を入力する。変更後は、他の端末のセッションをすべて失効させる。API の追加が必要
  - 実装(T14、2026-10-17): `POST /auth/password`(`{ currentPassword, newPassword }`、セッション cookie で認証)。現在のパスワードの誤りは 403 `wrong_password`(401 は管理画面がログイン切れとして扱うため使わない)。総当たり対策にログインと同じレート制限をかける。成功すると操作した端末以外のセッションを失効させ、`{ ok: true, revokedSessions }` を返す。他の端末に発行済みの短命 JWT(最大 15 分)は失効させない。トークンの再発行ができなくなった時点で止まる
- **所属しているサイト**: 所属しているサイトとロールの一覧。サイト選択画面と同じ情報
- **ログイン中の端末**: 当面は設けない(セッション一覧の API が無いため)。代わりに「他の端末からすべてログアウト」ボタンを置くかは 9 章の未決事項とする

## 7. 権限による出し分け

| 画面                                               | owner | editor | viewer |
| -------------------------------------------------- | ----- | ------ | ------ |
| 設定(一般・メンバー・モジュール・コンテンツタイプ) | 表示  | 非表示 | 非表示 |
| アカウント                                         | 表示  | 表示   | 表示   |

## 8. 運営コンソールとの関係

- 運営コンソールのメンバー一覧・剥奪はそのまま残す。owner がいなくなったテナントの救済や、不正利用への対応に使う
- テナントの作成・削除・slug の決定は、引き続き運営者だけが行う

## 9. 未決事項

メール送信の仕組みは今回導入しない(2026-10-17 決定、[棚卸し](./current-structure.md) 6.1)。招待リンク、パスワードを忘れたときの再設定、メールアドレスの変更は、導入する場合に改めて設計する。

- ロールの変更を即時に反映させる仕組み(トークンの強制再発行など)を設けるか
- 「他の端末からすべてログアウト」を設けるか
- 最終更新者の名前の表示([案 B](./b-home.md) 6 章・[案 D](./d-content-list.md) 10 章)に、メンバー一覧の API を流用するか
