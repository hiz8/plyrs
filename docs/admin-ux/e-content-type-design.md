# 案 E: コンテンツタイプの設計画面を利用者の言葉に寄せる 設計

[現状構造の棚卸し](./current-structure.md) の案 E(2026-10-17 採用)を具体化する。対象はコンテンツタイプの一覧・作成・編集画面(現 `routes/t/$tenantSlug/content-types/*` と `components/content-type-form.tsx`、[案 A](./a-navigation.md) の URL では `/t/:slug/settings/content-types`)と、その元になる型定義のデータ構造(`packages/metamodel`)。

この画面を使うのは owner(サイトを設計する人)で、WordPress なら ACF(Advanced Custom Fields)や CPT UI で投稿タイプとカスタムフィールドを作る人に当たる。

## 1. 目的

- 型の設計者が、技術用語(`text` `relation` `indexed` `cardinality` など)を知らなくても型を作れるようにする
- 設計した内容が、編集者の画面(入力フォーム・一覧・サイドバー)に分かりやすく現れるようにする。現状は、フィールドの key(snake_case)がそのまま入力フォームのラベルになっている

## 2. 型定義に追加する項目(メタモデルの変更)

いずれも任意項目として追加し、既存の型定義はそのまま有効とする。値が無いときの扱いを「既定」の列に示す。

### 2.1 フィールドに追加する項目

| 項目          | 内容                                                                           | 既定               |
| ------------- | ------------------------------------------------------------------------------ | ------------------ |
| `label`       | 表示名(例: 「タイトル」「公開日」)。入力フォームのラベル、一覧の列見出しに使う | key をそのまま表示 |
| `description` | 説明文。入力フォームの入力欄の下に補足として表示する                           | 表示しない         |

### 2.2 型に追加する項目

| 項目          | 内容                                                                               | 既定                                                        |
| ------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `description` | 型の説明。設定の型一覧と、ホームの「はじめに」に表示する                           | 表示しない                                                  |
| `titleField`  | タイトルとして使うフィールドの key。一覧・ホーム・関係の選択肢・パンくずに表示する | 最初の text フィールド(現行の `lib/record-label.ts` の挙動) |
| `listColumns` | 一覧に追加で表示するフィールドの key(最大 3 件)。例: 予約枠の開始日時              | 追加の列なし                                                |
| `menuOrder`   | サイドバーでの並び順(整数、昇順)                                                   | 表示名の五十音順(案 A 3.2 の当面の並び)                     |

### 2.3 変更の影響

- 型定義のスキーマ(`packages/metamodel/src/field-types.ts` と `content-type.ts`)は `strictObject` のため、項目を足すと旧版のコードは新しい定義を受け付けない。管理画面と API は同時にデプロイされるため問題にならないが、型定義を読む箇所はすべて同じ版のメタモデルを使う前提になる
- 公開 API の応答(公開版の `data`)には影響しない。追加する項目は型定義の中だけにある
- モジュールの型(`source: "plugin"`)も同じ項目を持てる。モジュールの定義(manifest)で表示名や説明を与える。モジュールの型は利用者が編集できない(現行どおり)

## 3. フィールドの種類の選び方

型の選択肢を、内部の型名ではなく利用者の言葉で並べる。内部の型と設定の組み合わせに対応づける。

| 画面上の種類                    | 内部の型と設定                                                  | 主な設定項目                            |
| ------------------------------- | --------------------------------------------------------------- | --------------------------------------- |
| テキスト(1 行)                  | `text`                                                          | 最大文字数                              |
| リッチテキスト                  | `richtext`                                                      | —                                       |
| 数値                            | `number`                                                        | 整数のみ                                |
| 日時                            | `datetime`                                                      | —                                       |
| チェックボックス(はい / いいえ) | `boolean`                                                       | —                                       |
| 選択肢                          | `select`                                                        | 選択肢の一覧、複数選択                  |
| 画像・ファイル                  | `relation`(`allowedTypes: ["asset"]`、`snapshotEmbed: "value"`) | 1 件 / 複数                             |
| 他のコンテンツへの参照          | `relation`(`allowedTypes` に asset 以外の型)                    | 参照できる型、1 件 / 複数、並び順を保持 |
| URL スラッグ                    | `text`(key `slug`、`unique: true`)                              | —                                       |
| JSON(上級者向け)                | `json`                                                          | —                                       |

- **画像・ファイル**: 現状は「関係」型を選び、許可する型に `asset` と手入力し、「公開時に値を埋め込む」に印を付ける必要がある。これを 1 つの種類にまとめる。埋め込みは既定で有効にする
- **他のコンテンツへの参照**: 「許可する型」をカンマ区切りの自由入力から、型の一覧から選ぶ複数選択に変える
- **URL スラッグ**: 公開 API の slug での取得(`records/:type/slug/:slug`)は「key が `slug` の unique な text フィールド」という暗黙の規約に依存している(`apps/api/src/projection/payload.ts` の `promoteSlug`)。この規約を種類として明示する。1 つの型に 1 つだけ置ける
- **JSON**: 一覧の最後に「上級者向け」として置く

## 4. 設定項目の言い換え

| 現在の表示                       | 新しい表示                                     | 補足の説明(入力欄の下に表示)                                    |
| -------------------------------- | ---------------------------------------------- | --------------------------------------------------------------- |
| フィールド key                   | API で使う名前                                 | 公開 API の応答でこの名前が使われます。英小文字・数字・`_` のみ |
| 必須                             | 必須                                           | —                                                               |
| indexed                          | 公開 API で絞り込み・並べ替えに使う            | 公開 API の検索条件や並び順に使えるようになります               |
| unique                           | 同じ値を許可しない                             | 他のコンテンツと同じ値は保存できません                          |
| maxLength                        | 最大文字数                                     | —                                                               |
| 整数のみ                         | 整数のみ                                       | —                                                               |
| 選択肢(1 行 1 件、value=ラベル)  | 選択肢                                         | 行ごとに「表示名」と「API で使う値」を入力する表形式に変える    |
| カーディナリティ one / many      | 1 件だけ / 複数                                | —                                                               |
| 順序を保持                       | 並び順を保持                                   | 選んだ順番を公開 API の応答でも保ちます                         |
| 公開時に値を埋め込む(asset 限定) | (画像・ファイルでは既定で有効にし、表示しない) | —                                                               |

`indexed` と `unique` の意味は design-spec §5「フィールド制約は宣言ベース」に従う。

## 5. 画面の構成

### 5.1 型の一覧(設定 › コンテンツタイプ)

- 列: 表示名(と説明)、フィールド数、コンテンツの件数、操作
- 現在の `key` `source` `version` の列は外す。key は表示名の下に小さく「API 名: `news`」と出す
- システム型(`asset`)は一覧に出さない(メディアとして別に扱う)
- モジュールの型は「予約(モジュール)」のように見出しで分け、編集不可と分かる表示にする
- 行をドラッグして並べ替えると、`menuOrder` を更新する(サイドバーの並び順になる)

### 5.2 型の作成・編集

```
┌────────────────────────────────────────────────────────────┐
│ 設定 › コンテンツタイプ › お知らせ                                │
│ お知らせ                                          [保存]       │
│                                                            │
│ 表示名 [お知らせ        ]   API 名 [news   ] ← 作成後は変更不可    │
│ 説明   [サイトのお知らせ  ]                                     │
│                                                            │
│ フィールド                                                    │
│ ┌──────────────────────────────────────────────────────┐   │
│ │ ⠿ タイトル        テキスト(1 行)  必須   タイトルに使う  [編集]│   │
│ │ ⠿ URL スラッグ    URL スラッグ    必須              [編集]│   │
│ │ ⠿ 本文           リッチテキスト                      [編集]│   │
│ │ ⠿ アイキャッチ     画像・ファイル                      [編集]│   │
│ └──────────────────────────────────────────────────────┘   │
│ [+ フィールドを追加]                                           │
│                                                            │
│ 一覧に表示する列  [公開日 ▾] [＋]                                │
└────────────────────────────────────────────────────────────┘
```

- フィールドは 1 行 1 件の一覧で表示し、「編集」で詳細の設定(4 章の項目)を開く。現在のように全フィールドの全設定を常に展開する形はやめる
- 行の左端のつまみ(⠿)をドラッグして並べ替える。並び順は入力フォームの並び順になる(`fields` 配列の順。データへの影響は無い)
- 「タイトルに使う」は、テキスト(1 行)のフィールドのどれか 1 つに付ける(`titleField`)
- 「フィールドを追加」では、まず 3 章の種類を選び、次に表示名を入力する
- **API で使う名前(key)の入力**: 表示名を英数字で入力した場合は、それを元に key を自動で入れる(例: 「Title」→ `title`)。日本語の場合は自動生成せず、入力を求める。key は公開 API の応答に現れ、フロントエンドの開発者が読むため、`field_1` のような意味の無い名前を自動で付けることは避ける
- 保存したあとは key を変更できない旨を、入力欄の補足に表示する(現状も変更は削除 + 追加として扱われる)

### 5.3 変更時の注意の出し方

現在は型の編集画面の冒頭に、技術的な注意文(遅延適合の説明)が常に表示されている。これを、影響のある操作をしたときだけ表示する形に変える。

| 操作                   | 表示する注意                                                                                                                                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| フィールドの削除       | 「このフィールドは入力フォームから消えます。入力済みの値はデータ上に残り、同じ API 名でフィールドを作り直すと再び表示されます」(公開済みの版と公開 API の応答にいつまで値が残るかは、実装時に投影の挙動を確認して文言を決める) |
| フィールドの種類の変更 | 「入力済みの値は自動では変換されません。値が新しい種類に合わない場合、そのコンテンツを次に保存するときに入力し直す必要があります」                                                                                             |
| 必須に変更             | 「既に作成済みで値が空のコンテンツは、次に保存するときに入力が必要になります」                                                                                                                                                 |

注意の内容は design-spec §4.2(読み取りは寛容、未知フィールドは破棄せず保持、書き込み時に現行定義で検証)に基づく。

### 5.4 型の削除

- 現状は型を削除する手段が無い。コンテンツが 0 件の型に限り削除できるようにする(API の追加が必要)
- コンテンツが 1 件以上ある型は削除できず、「先にコンテンツを削除してください」と案内する。コンテンツごと消す操作は、誤操作の影響が大きいため設けない

## 6. 編集者の画面への反映

| 画面                   | 反映される項目                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------- |
| サイドバー(案 A)       | 型の表示名、`menuOrder`                                                                     |
| コンテンツの一覧(案 D) | `titleField`(タイトル列と検索対象)、`listColumns`(追加の列)、フィールドの `label`(列見出し) |
| 作成・編集画面(案 C)   | フィールドの `label`・`description`・並び順、必須の印                                       |
| ホーム(案 B)           | `titleField`、型の `description`(はじめての利用の案内)                                      |
| 関係の選択肢・パンくず | `titleField`                                                                                |

## 7. 未決事項

- 型の削除 API の仕様(削除済みのコンテンツ `deletedAt` が残っている場合の扱い、公開版の扱い)
- テキスト(複数行)を独立した種類として設けるか。現在のメタモデルには 1 行と複数行の区別が無い(`text` のみ)ため、入力欄の見た目の指定を型定義に持たせる必要がある
- 日付のみ(時刻なし)の種類を設けるか。現在は `datetime` のみ
