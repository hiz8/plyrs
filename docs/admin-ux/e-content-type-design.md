# 案 E: コンテンツタイプの設計画面を利用者の言葉に寄せる 設計

[現状構造の棚卸し](./current-structure.md) の案 E(2026-10-17 採用)を具体化する。対象はコンテンツタイプの一覧・作成・編集画面(現 `routes/t/$tenantSlug/content-types/*` と `components/content-type-form.tsx`、[案 A](./a-navigation.md) の URL では `/t/:slug/settings/content-types`)と、その元になる型定義のデータ構造(`packages/metamodel`)。

この画面を使うのは owner(サイトを設計する人)で、WordPress なら ACF(Advanced Custom Fields)や CPT UI で投稿タイプとカスタムフィールドを作る人に当たる。

## 1. 目的

- 型の設計者が、技術用語(`text` `relation` `indexed` `cardinality` など)を知らなくても型を作れるようにする
- 設計した内容が、編集者の画面(入力フォーム・一覧・サイドバー)に分かりやすく現れるようにする。現状は、フィールドの key(snake_case)がそのまま入力フォームのラベルになっている

## 2. 型定義に追加する項目(メタモデルの変更)

いずれも任意項目として追加し、既存の型定義はそのまま有効とする。値が無いときの扱いを「既定」の列に示す。

### 2.1 フィールドに追加する項目

| 項目          | 内容                                                                           | 既定               |
| ------------- | ------------------------------------------------------------------------------ | ------------------ |
| `label`       | 表示名(例: 「タイトル」「公開日」)。入力フォームのラベル、一覧の列見出しに使う | key をそのまま表示 |
| `description` | 説明文。入力フォームの入力欄の下に補足として表示する                           | 表示しない         |

### 2.2 型に追加する項目

| 項目          | 内容                                                                               | 既定                                                        |
| ------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `description` | 型の説明。設定の型一覧と、コンテンツの一覧の空状態(その型が 0 件のとき)に表示する                           | 表示しない                                                  |
| `titleField`  | タイトルとして使うフィールドの key。一覧・ホーム・関係の選択肢・パンくずに表示する | 最初の text フィールド(現行の `lib/record-label.ts` の挙動) |
| `listColumns` | 一覧に追加で表示するフィールドの key(最大 3 件)。例: 予約枠の開始日時              | 追加の列なし                                                |
| `menuOrder`   | サイドバーでの並び順(整数、昇順)                                                   | 表示名の五十音順(案 A 3.2 の当面の並び)                     |

(2026-10-24、持ち越し): 型の `description` の表示場所は、ホームの「はじめに」(型が 0 件のカードに説明を出す場所が無い)ではなく、コンテンツの一覧の空状態の説明文とした。未設定なら従来の文のまま(K1、ユーザー裁定)

### 2.3 変更の影響

- 型定義のスキーマ(`packages/metamodel/src/field-types.ts` と `content-type.ts`)は `strictObject` のため、項目を足すと旧版のコードは新しい定義を受け付けない。管理画面と API は同時にデプロイされるため問題にならないが、型定義を読む箇所はすべて同じ版のメタモデルを使う前提になる
- 公開 API の応答(公開版の `data`)には影響しない。追加する項目は型定義の中だけにある
- モジュールの型(`source: "plugin"`)も同じ項目を持てる。モジュールの定義(manifest)で表示名や説明を与える。モジュールの型は利用者が編集できない(現行どおり)

## 3. フィールドの種類の選び方

型の選択肢を、内部の型名ではなく利用者の言葉で並べる。内部の型と設定の組み合わせに対応づける。

| 画面上の種類                    | 内部の型と設定                                                  | 主な設定項目                            |
| ------------------------------- | --------------------------------------------------------------- | --------------------------------------- |
| テキスト(1 行)                  | `text`                                                          | 最大文字数                              |
| リッチテキスト                  | `richtext`                                                      | —                                       |
| 数値                            | `number`                                                        | 整数のみ                                |
| 日時                            | `datetime`                                                      | —                                       |
| チェックボックス(はい / いいえ) | `boolean`                                                       | —                                       |
| 選択肢                          | `select`                                                        | 選択肢の一覧、複数選択                  |
| 画像・ファイル                  | `relation`(`allowedTypes: ["asset"]`、`snapshotEmbed: "value"`) | 1 件 / 複数                             |
| 他のコンテンツへの参照          | `relation`(`allowedTypes` に asset 以外の型)                    | 参照できる型、1 件 / 複数、並び順を保持 |
| URL スラッグ                    | `text`(key `slug`、`unique: true`)                              | —                                       |
| JSON(上級者向け)                | `json`                                                          | —                                       |

- **画像・ファイル**: 現状は「関係」型を選び、許可する型に `asset` と手入力し、「公開時に値を埋め込む」に印を付ける必要がある。これを 1 つの種類にまとめる。埋め込みは既定で有効にする
- **他のコンテンツへの参照**: 「許可する型」をカンマ区切りの自由入力から、型の一覧から選ぶ複数選択に変える
- **URL スラッグ**: 公開 API の slug での取得(`records/:type/slug/:slug`)は「key が `slug` の unique な text フィールド」という暗黙の規約に依存している(`apps/api/src/projection/payload.ts` の `promoteSlug`)。この規約を種類として明示する。1 つの型に 1 つだけ置ける
- **JSON**: 一覧の最後に「上級者向け」として置く

(2026-10-20、V4-E): 画面上の種類と内部の型の対応(`kindOf`)は、`slug` = `text` かつ key `slug` かつ `unique: true`、`asset` = `relation` かつ `allowedTypes` がちょうど `["asset"]`(`snapshotEmbed: "value"` を常に付ける)、`reference` = それ以外の `relation`、他は 1:1。読む側(record-form)の判定と同じ(E12)

(2026-10-20、V4-E): 種類の変更はパネルの「種類」`Select` から行う。変えると種類ごとの設定は新しい種類の既定に戻り、表示名・API 名・説明・必須は保つ。「URL スラッグ」は API 名が `slug` のときだけ選べる。種類の選択ダイアログでは、型に既に URL スラッグがあればカードを無効にして理由「この型には既に URL スラッグがあります」(`disabledReason`)を出す(E13)

(2026-10-20、V4-E): 「参照できる型」は `CheckboxGroup`。候補は利用者の型とモジュールの型(`source !== "system"`)から自分自身(編集中の型の key)を除いたもので、表示は型名。新規作成(key 未定)では全部。1 件以上必須(E22)

(2026-10-20、V4-E): 種類の選択ダイアログは `ModalDialog` に `size?: "md" | "lg"`(md 440px = 現行、lg 640px)を足して `lg` で描く。題は `Heading slot="title"`、段階は題の下の `font.caption`(E23)

## 4. 設定項目の言い換え

| 現在の表示                       | 新しい表示                                     | 補足の説明(入力欄の下に表示)                                    |
| -------------------------------- | ---------------------------------------------- | --------------------------------------------------------------- |
| フィールド key                   | API で使う名前                                 | 公開 API の応答でこの名前が使われます。英小文字・数字・`_` のみ |
| 必須                             | 必須                                           | —                                                               |
| indexed                          | 公開 API で絞り込み・並べ替えに使う            | 公開 API の検索条件や並び順に使えるようになります               |
| unique                           | 同じ値を許可しない                             | 他のコンテンツと同じ値は保存できません                          |
| maxLength                        | 最大文字数                                     | —                                                               |
| 整数のみ                         | 整数のみ                                       | —                                                               |
| 選択肢(1 行 1 件、value=ラベル)  | 選択肢                                         | 行ごとに「表示名」と「API で使う値」を入力する表形式に変える    |
| カーディナリティ one / many      | 1 件だけ / 複数                                | —                                                               |
| 順序を保持                       | 並び順を保持                                   | 選んだ順番を公開 API の応答でも保ちます                         |
| 公開時に値を埋め込む(asset 限定) | (画像・ファイルでは既定で有効にし、表示しない) | —                                                               |

`indexed` と `unique` の意味は design-spec §5「フィールド制約は宣言ベース」に従う。

実装状況(2026-10-20、V3): 作成・編集画面(案 C)で、フィールドの `label` / `description` を使う。ラベルは `label ?? key`、`description` は入力欄の下に出す(R5)。

(2026-10-20、V4-E): 選択肢の表は、行ごとに「表示名」「API で使う値」の `TextField`(値は等幅)と `IconButton`「{表示名}を外す」を置き、下に「選択肢を追加」。適用時に 1 件以上・値が空でない・値が重複しないことを検証し、表の下にエラーを出す(E34)。件数の表示はパネルでは `SegmentedControl`(ラベル「件数」、`one`「1 件だけ」/ `many`「複数」)、行のタグは「1 件だけ」/「複数」(画像・ファイルと参照だけ)(E35)

## 5. 画面の構成

### 5.1 型の一覧(設定 › コンテンツタイプ)

- 列: 表示名(と説明)、フィールド数、コンテンツの件数、操作
- 現在の `key` `source` `version` の列は外す。key は表示名の下に小さく「API 名: `news`」と出す
- システム型(`asset`)は一覧に出さない(メディアとして別に扱う)
- モジュールの型は「予約(モジュール)」のように見出しで分け、編集不可と分かる表示にする
- 行をドラッグして並べ替えると、`menuOrder` を更新する(サイドバーの並び順になる)
- 画面の形(D3 で確定、2026-10-18): 設定は見出し「設定」の下の 4 つのタブ(一般 / コンテンツタイプ / メンバー / モジュール)で切り替える。利用者の型は表(つまみ・表示名と説明・フィールド数・コンテンツ件数・編集)で、コンテンツ 0 件の型にだけ「削除」のテキストリンクを出す(5.4)。モジュールの型は「予約(モジュール)」の見出しで分け、つまみ無し・「フィールドを見る」(読み取り専用)

(2026-10-20、V4-E):
- 文言: 一覧の主操作「コンテンツタイプを作成」、新規の h1「コンテンツタイプを作成」、パンくず「作成」、主操作「作成」(現行の「追加」から変える)。編集の主操作は「保存」。どちらも補助操作「キャンセル」で一覧へ戻る(確認なし)(E5・E32)
- 行は `Table` ではなく `SortableList`(RAC `GridList` + `useDragAndDrop`)で描く。行 44px(`size.row`)、列は CSS グリッド `1fr 110px 120px 180px`(狭い画面は「フィールド」を隠す)。列見出しは一覧の上の 1 行。行の名前のリンクは編集へ(RAC `Link`)。マウス・タッチ・キーボード(つまみにフォーカス → Enter / Space でつかむ → ↑↓ → Enter / Space で置く)で並べ替えられる(E1・E6)
- コンテンツの件数は同期データ(`useRecordsOfTypes`、`deletedAt === null` だけ)から数える。同期が済むまでは件数の列を `Skeleton` にし、「削除」を出さない(0 件と未取得を区別できないため)(E7)
- モジュールの型は `pluginId` で分け、見出しはモジュールの `name`(取れなければ `pluginId`)に `Badge`「モジュール」と注記を添える。グループの順は modules の順、型の順は `navTypes` の順(残りは名前順)。無効化済みのモジュールの型も出す。システム型(`source: "system"`)は出さない。つまみ無し・「フィールドを見る」(`/settings/content-types/$typeKey/edit`)(E8)
- 「フィールドを見る」は同じ編集ルートを `mode="view"` で描く。h1 は型名、`meta`「モジュールの型(編集できません)」、保存・キャンセル・追加・つまみ・一覧に表示する列の変更は無し、行の「詳細」でパネルを読み取り専用(入力は `isReadOnly`、下部は「閉じる」だけ)で開く。`type:manage` の無い人と、URL で直接開いた system 型も同じ(E9)
- `menuOrder` の保存: ドロップ後の並びの index(0〜)を `menuOrder` にし、値が変わる型だけ上から順に `putContentType` する(version はサーバーが上げる)。処理中は `SortableList` を `isDisabled`。成功のトーストは出さない。失敗はトースト「並び順を保存できませんでした」と一覧の取り直し。新規作成の型は `menuOrder` 未設定(サイドバーの末尾)のまま(E10)

### 5.2 型の作成・編集

```
┌────────────────────────────────────────────────────────────┐
│ 設定 › コンテンツタイプ › お知らせ                                │
│ お知らせ                                          [保存]       │
│                                                            │
│ 表示名 [お知らせ        ]   API 名 [news   ] ← 作成後は変更不可    │
│ 説明   [サイトのお知らせ  ]                                     │
│                                                            │
│ フィールド                                                    │
│ ┌──────────────────────────────────────────────────────┐   │
│ │ ⠿ タイトル        テキスト(1 行)  必須   タイトルに使う  [編集]│   │
│ │ ⠿ URL スラッグ    URL スラッグ    必須              [編集]│   │
│ │ ⠿ 本文           リッチテキスト                      [編集]│   │
│ │ ⠿ アイキャッチ     画像・ファイル                      [編集]│   │
│ └──────────────────────────────────────────────────────┘   │
│ [+ フィールドを追加]                                           │
│                                                            │
│ 一覧に表示する列  [公開日 ▾] [＋]                                │
└────────────────────────────────────────────────────────────┘
```

- フィールドは 1 行 1 件の一覧(48px、つまみ・表示名と API 名・種類・必須などのタグ・「編集」)で表示し、「編集」で右側のパネル(幅 420px)に詳細の設定(4 章の項目)を開く。一覧を見ながら設定できるようにするため。狭い画面ではモーダルに切り替える。現在のように全フィールドの全設定を常に展開する形はやめる(D3 で確定)
- パネルの最下部に「このフィールドを削除」(危険色のテキストリンク)と「キャンセル」「適用」を置く
- 行の左端のつまみ(⠿)をドラッグして並べ替える。並び順は入力フォームの並び順になる(`fields` 配列の順。データへの影響は無い)
- 「タイトルに使う」は、テキスト(1 行)のフィールドのどれか 1 つに付ける(`titleField`)
- 「フィールドを追加」では、2 段階のダイアログで、まず 3 章の種類を選び、次に表示名と API 名を入力する(D3 で確定)。1 段目は「基本」(テキスト・リッチテキスト・数値・日時・チェックボックス・選択肢)と「他のデータとつなぐ」(画像・ファイル・他のコンテンツへの参照・URL スラッグ)を 3 列のカード(アイコン・名前・短い説明)で並べ、JSON は区切り線の下に「上級者向け」として薄く置く。追加したフィールドは一覧の末尾に入り、続けて右パネルで詳細を設定できる
- **API で使う名前(key)の入力**: 表示名を英数字で入力した場合は、それを元に key を自動で入れる(例: 「Title」→ `title`)。日本語の場合は自動生成せず、入力を求める。key は公開 API の応答に現れ、フロントエンドの開発者が読むため、`field_1` のような意味の無い名前を自動で付けることは避ける
- 保存したあとは key を変更できない旨を、入力欄の補足に表示する(現状も変更は削除 + 追加として扱われる)

(2026-10-20、V4-E):
- パネルは `SidePanel`(RAC `Dialog` を右に固定、420px の非モーダル)で実装する。開くとパネルへ、閉じると開いた「編集」へフォーカスを戻し、Esc で閉じる。狭い画面は CSS だけで全面のシートにする(フォーカスの閉じ込めは無いため厳密なモーダルではない)。一覧を見ながら別の行の「編集」や並べ替えができることを優先した(E2)。パネルを開いている間は本文の入れ物に右 420px の余白を取り(狭い画面は 0)、行の「編集」が隠れないようにする(E29)
- 「保存」の有効条件: 編集は変更があり、かつ入力が有効なときだけ。新規は表示名・API 名・フィールド 1 件以上がそろい、API 名に誤りが無いまで無効。パネルを開いている間はどちらも無効にし、理由「フィールドの設定を適用するか、キャンセルしてください」をツールチップで出す。パネルは「適用」で編集中の下書きに写し、「キャンセル」「閉じる」「Esc」は捨てる(E4・E24)
- (2026-10-21、V4-E 実行中の裁定)設定が未完了のフィールド(選択肢が 0 件、参照できる型が 0 件、選択肢の表示名や値が空)が 1 つでもあると保存できず、その行に「設定が未完了」のタグを出す。フィールドの表示名は型定義のスキーマどおり任意で、無くても型は保存できる(V4-E 以前のデータはすべて表示名が無いため)。パネルで適用するときだけ表示名を必須にする(E4 の補足)
- API 名の自動生成は `suggestKey(label)`: 英字を含むときだけ、小文字化し `[a-z0-9]` 以外の連続を `_` にし、先頭の英字より前と末尾の `_` を落とす(「Sub-Title」→ `sub_title`、「2nd Title」→ `nd_title`)。日本語だけなら空。`autoFill(prevLabel, prevValue, nextLabel)` は値が前回の提案と同じ(または空)の間だけ追従し、手で変えたら止める。型の API 名、フィールドの API 名、選択肢の「API で使う値」に同じ規則を使う(E14)
- 保存済みフィールドの API 名は変更不可。パネルでは `isDisabled` と補足「保存したあとは変更できません」を出し、本セッションで追加した未保存のフィールド(`isNew`)だけ変えられる(E16)
- 「タイトルに使う」はパネルの `Checkbox`(テキスト(1 行)だけ)。付けると他の指定は外れる(1 つだけ)。行のタグは実効のタイトル(`titleFieldKey` の指定、無ければ最初のテキスト)に出す。指定したフィールドの種類を変えたり消したりしたら指定を落とす(E19)。(2026-10-21、V4-E 実行中の裁定)暗黙のタイトル(指定が無く最初のテキスト)はパネルで適用しても明示値に変えず、チェックは無効表示にして既定である旨を補足する
- 「一覧に表示する列」は、選択中をチップ(`Badge tone="accent"` と `IconButton`「{表示名}を外す」)で示し、追加は `Select`(ラベル非表示「列を追加」、候補は未選択のフィールド全部)。`LIST_COLUMNS_MAX` の 3 件で `Select` を無効にする(E20)
- 種類のカードは `Button`(`aria-pressed` で選択中)、「次へ」で 2 段目へ進み、「種類を選び直す」で 1 段目に戻る(選択は保つ)。URL スラッグを選んだときの 2 段目は表示名の初期値「URL スラッグ」、API 名は `slug` 固定(`isDisabled`)(E33)
- 保存の結果: 成功はトースト「作成しました」/「保存しました」と `content-types` の invalidate、一覧へ戻る。失敗はトースト(`errorMessage(cause, "保存できませんでした")`)で画面に留まり、旧の `role="alert"` バナーはやめる(E25)
- (2026-10-24、持ち越し)型の編集画面に離脱ガードを足す。新規は入力済み、編集は変更ありのときに、画面の移動で「このまま移動すると、コンテンツタイプの変更は失われます。」を確認ダイアログ(`alertdialog`、「編集を続ける」/「破棄して移動」)で出す。閲覧(`view`)は対象外で、保存成功後と削除後の移動はガードしない(K4)

### 5.3 変更時の注意の出し方

現在は型の編集画面の冒頭に、技術的な注意文(遅延適合の説明)が常に表示されている。これを、影響のある操作をしたときだけ表示する形に変える。

| 操作                   | 表示する注意                                                                                                                                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| フィールドの削除       | 「このフィールドは入力フォームから消えます。入力済みの値はデータ上に残り、同じ API 名でフィールドを作り直すと再び表示されます」(公開済みの版と公開 API の応答にいつまで値が残るかは、実装時に投影の挙動を確認して文言を決める) |
| フィールドの種類の変更 | 「入力済みの値は自動では変換されません。値が新しい種類に合わない場合、そのコンテンツを次に保存するときに入力し直す必要があります」                                                                                             |
| 必須に変更             | 「既に作成済みで値が空のコンテンツは、次に保存するときに入力が必要になります」                                                                                                                                                 |

注意の内容は design-spec §4.2(読み取りは寛容、未知フィールドは破棄せず保持、書き込み時に現行定義で検証)に基づく。

表示する位置(D3 で確定): 画面の冒頭には出さず、影響のある操作をした行の直下に警告色のインライン表示を置き、行には「必須に変更」「種類を変更」のタグを付ける。件数が分かるものは「(12 件)」のように添える。フィールドの削除だけは確認ダイアログ(危険色の「削除する」)も挟み、公開 API の応答からも項目が消えることを警告する。(2026-10-20、V4-E)実装時の確認で、値は公開応答に残ることが分かった。E17 を参照。API 名の入力エラー(使えない文字・重複・システムが使う名前)は入力欄の下にエラー色で例を添えて示す。

(2026-10-20、V4-E): 注意の件数は削除済みを除くコンテンツで数える。「必須に変更」は値が空(`undefined` / `null` / `""` / `[]`)のもの、「種類を変更」は値があるもの。同期が済んでいない間は件数なしの文にする(E18)。API 名の検証文言は、空「API で使う名前を入力してください」/ 使えない文字「英小文字・数字・_ だけが使えます。例: {suggestKey(入力) または title}」/ 重複「「{key}」は「{表示名}」で既に使われています」/ 予約語(`SYSTEM_FIELD_KEYS`)「「{key}」はシステムが使う名前のため使えません」。型の API 名は既存の型(システム型・モジュールの型を含む)と重複不可、パターンは `FIELD_KEY_PATTERN`。入力があれば即時に出す(E15)
(2026-10-20、V4-E): フィールドの削除の保留に決着。保存済みは `ConfirmDialog tone="danger"`、未保存(`isNew`)は確認なしで一覧から消す。投影を確認した結果、公開は record の data をそのまま写し(`do/publish.ts`)、公開 API は `data` を `fields` としてそのまま返す(`public/serialize.ts`)ため、消したフィールドの値は公開応答に残り続け、`projection_fields` から消えて絞り込み・並べ替えに使えなくなるだけである。注記はこの事実を書く(E17)

### 5.4 型の削除

- 現状は型を削除する手段が無い。コンテンツが 0 件の型に限り削除できるようにする(API の追加が必要)
- コンテンツが 1 件以上ある型は削除できず、「先にコンテンツを削除してください」と案内する。コンテンツごと消す操作は、誤操作の影響が大きいため設けない
- API の仕様(2026-10-17、ロードマップ T7 で実装): `DELETE /v1/t/:tenantId/content-types/:key`。`type:manage`(owner)だけが実行できる
  - 削除済みのコンテンツ(トゥームストーン)は件数に数えず、同期の削除伝搬のために残す
  - コンテンツの削除時に公開版は取り下げられるため、公開版は通常残らない。残っていた場合は削除を拒否する
  - 削除できるのは利用者が作った型だけ。システムの型(メディア)とモジュールの型は拒否する
  - 他の型の関係フィールドが削除した型を指していても妨げない(関係はソフト参照)
  - 型ごとに作ったインデックス用の生成列も片付ける。削除後に同じ key で型を作り直せる
  - コンテンツが残っている場合は 409 `type_not_empty` を返す
  - 公開投影 D1 のカタログ(`projection_fields`)に残る削除した型の行は、オーナーが再投影するまで残る。公開レコードは 0 件なので内容は漏れず、その型でのフィルタが 400 ではなく空配列を返すだけになる(型定義からフィールドを外した場合と同じ既存の挙動)
  - クライアントの `CollectionRegistry.sync`(`packages/sync-client/src/tanstack.ts`)は型の追加だけを扱う。`getTypes()` は全置換されるのでサイドバーからは消えるが、消えた型のコレクションは次の全再同期まで残る。削除の画面(V4)を作るときに、エントリを破棄するかを決める
  - オフラインでその型の下書きを持つ端末は、再接続時に `unknown_type` で拒否され、下書きは失われる。0 件の型だけを消せる仕様上避けられないため、削除確認の文言を考える際の前提とする
- (2026-10-20、V4-E): 削除の確認は `ConfirmDialog tone="danger"`。題「「{型名}」を削除しますか？」、本文「コンテンツが 0 件のため削除できます。削除後は同じ API 名で作り直せます。」、注記(warning)「オフラインの端末にこの型の下書きが残っている場合、再接続時にその下書きは失われます」、実行「削除する」。成功は `content-types` の invalidate とトースト、409 `type_not_empty` はトースト(`ERROR_MESSAGES`)と invalidate。`CollectionRegistry` のエントリは破棄しない(型一覧から消えれば参照されず、次の全再同期で消える)(E11)
