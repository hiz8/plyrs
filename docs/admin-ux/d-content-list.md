# 案 D: コンテンツ一覧の公開状態とフィルタ 設計

[現状構造の棚卸し](./current-structure.md) の案 D(2026-10-17 採用)を具体化する。対象はコンテンツの一覧画面(現 `routes/t/$tenantSlug/records/$typeKey/index.tsx`、[案 A](./a-navigation.md) の URL では `/t/:slug/content/:typeKey`)。モジュールの型の一覧も同じ画面を使う。メディアの一覧は案 F で別に扱う。

## 1. 目的

WordPress の投稿一覧(「すべて / 公開済み / 下書き」のタブ、検索、一括操作、ページ送り)に慣れた利用者が、目的のコンテンツを探し、公開状態を一目で確認できるようにする。現状の一覧は更新日時の降順の表だけで、公開中かどうかが分からず、検索・絞り込み・一括操作も無い。

## 3. 公開状態の表示とタブ

### 3.1 公開状態

公開状態(`published_snapshots` の有無、design-spec §7)とワークフロー状態(`records.status`)は、データ上の分離を保ったまま、一覧では別の列に並べる。

| 公開列の表示              | 条件                                                               |
| ------------------------- | ------------------------------------------------------------------ |
| 公開中                    | 公開版があり、公開後に編集されていない                             |
| 公開中 ● 未反映の変更あり | 公開版があり、`record.version > sourceVersion`(公開後に編集された) |
| 未公開                    | 公開版が無い                                                       |

「未反映の変更あり」の判定は、編集画面の公開状態パネル(現 `components/publication-panel.tsx`)と同じにする。

### 3.2 タブ

WordPress の「すべて / 公開済み / 下書き / ゴミ箱」に相当するタブを、公開状態の軸で置く。

| タブ             | 対象                                 |
| ---------------- | ------------------------------------ |
| すべて           | アーカイブ以外のすべて               |
| 公開中           | 公開中(未反映の変更ありも含む)       |
| 未反映の変更あり | 公開中のうち、公開後に編集されたもの |
| 未公開           | 公開版が無いもの(アーカイブを除く)   |
| アーカイブ       | ステータスがアーカイブのもの         |

- アーカイブは普段の一覧から外したものとして扱い、「アーカイブ」タブ以外(公開中・未反映の変更ありを含む)には出さない。公開版が残っているアーカイブ済みのものも同じ。どのタブも「すべて」の部分集合になる
- 各タブに件数を表示する。件数が 0 のタブは「すべて」以外を薄く表示する
- アーカイブは「すべて」に含めない。WordPress のゴミ箱と同じく、普段の一覧から外したものとして扱う。アーカイブしても公開は維持される仕様(現 `status-control.tsx` の警告)のため、アーカイブのタブでも公開列は表示する

## 4. 絞り込みと検索

- **ステータス**: ドロップダウンで 下書き / レビュー中 / 公開準備完了 を選べる(アーカイブはタブで扱う)。タブとの組み合わせで「公開中 かつ 下書き」のような絞り込みができる
- **検索**: タイトルの部分一致で絞り込む。タイトルは現状「最初の text フィールド」(`lib/record-label.ts`)で、案 E でタイトル用フィールドを指定できるようになったらそれに従う。入力に合わせて即時に絞り込む
- 絞り込みと検索は、管理画面が同期で保持しているレコードに対して行う。サーバーへの問い合わせは不要

## 5. 列と並べ替え

- 列: 選択(チェックボックス)、タイトル、公開、ステータス、更新日時
- 現在の `version` 列は廃止する。更新日時は相対表記(「10 分前」)にし、ホバーで日時を出す(案 H)
- 並べ替え: タイトル(五十音順)と更新日時で並べ替えられる。既定は更新日時の新しい順
- タイトルをクリックすると編集画面へ移る。行にマウスを乗せると、タイトルの下に「編集」「削除」の操作リンクを出す(WordPress の行アクションと同じ)
- 型ごとの列の追加(例: 予約枠の開始日時、イベントの開催日)は、型の定義に一覧の列を指定できるようにする必要があり、案 E で扱う(10 章)

## 6. 一括操作

- 行のチェックボックスで選び、「一括操作」から実行する。見出し行のチェックボックスで表示中のページを全選択する
- 操作: 公開 / 公開を取り下げ / ステータスを変更 / 削除
- 公開と公開の取り下げは、レコードごとの既存 API(`POST .../publish` / `.../unpublish`)を順に呼ぶ。一括用の API は追加しない(件数が多くないうちはこれで足りる)
- ステータスの変更と削除は、同期経路で 1 件ずつ書き込む
- 実行中は進捗(「3 / 10 件」)を表示し、終わったら結果をトーストで知らせる。一部が失敗した場合は「8 件を公開しました。2 件は公開できませんでした」と件数を分けて示し、失敗したものを選択状態で残す
- 「公開を取り下げ」と「削除」は確認ダイアログを経て実行する(案 H の共通部品)
- viewer にはチェックボックスと一括操作を表示しない。行アクションも「表示」だけにする

## 7. ページ送り

- 1 ページ 20 件を既定とし、20 / 50 / 100 件から選べる
- データは手元にあるため、ページ送りは画面側で行う

## 8. URL への状態の保持

- タブ・ステータス・検索語・並べ替え・ページを URL のクエリに持たせる(例: `?tab=unpublished-changes&status=draft&page=2`)
- ブラウザの戻る操作で直前の絞り込みに戻れるようにするため。また、ホーム([案 B](./b-home.md))の「確認待ち」から、絞り込み済みの一覧へ直接リンクできるようにするため

## 9. 公開状態の取得

公開状態は同期の対象外(design-spec §10.1)で、現状はレコード 1 件ごとの API(`GET /:tenantId/records/:recordId/publication`)でしか取れない。一覧で全件分を 1 件ずつ取得するのは避けたいので、型ごとにまとめて取得する API を追加する。

- 追加する API: `GET /v1/t/:tenantId/publications?type=:typeKey`
- 返す内容: 公開中のレコードごとに `recordId` / `publishedAt` / `sourceVersion` だけ(公開版の本文は返さない)
- `type` を省略すると全型分を返す。ホーム(案 B)の「未反映の変更あり」の集計にはこちらを使う
- DO 内の `published_snapshots` は `type` 列を持つため(`packages/db/src/schema.ts`)、DO 内の 1 クエリで返せる。`(type, record_id)` の索引でフルスキャンを避ける
- 1 回の応答は最大 1000 件で、`record_id` 昇順のカーソル(`cursor` / `nextCursor`)でページを辿る。管理画面はタブの件数に全件が要るため最後のページまで取得して連結する。並びは `record_id` 昇順の安定順序で、作成順の約束ではない
- 取得のタイミング: 一覧を開いたとき、画面にフォーカスが戻ったとき、自分が公開・取り下げ・レコード削除をした直後(取得結果は 5 秒間使い回す)。他の利用者が公開したことは即時には反映されない(公開は同期経路を通らないため)。この遅れは画面に戻ったときの再取得で補う

## 10. 未決事項

- 型ごとに一覧の列を指定できるようにするか(案 E の型設計で、表示名やタイトル用フィールドの指定とあわせて決める)
- 最終更新者の列を出すか(案 B の 6 章と同じく、案 G のメンバー情報の取得方法とあわせて決める)
- 件数が非常に多い型(目安として数千件以上)での表示性能。手元のデータで絞り込む方式は、同期で全件を保持していることが前提になっている
