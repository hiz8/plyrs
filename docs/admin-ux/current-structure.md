# 管理画面の現状構造の棚卸し

管理画面(`apps/admin`)の UX 再構築に向けて、現在の画面・ナビゲーション・主要操作を棚卸しし、WordPress などの一般的な CMS 管理画面と対比して課題と再構築の方向性の候補をまとめる。コード変更は伴わない。

- 調査対象: `main` の `4c40c02` 時点の `apps/admin/src`(routes / components / router.tsx)
- 想定ユーザー: WordPress など既存 CMS の利用経験があるテナント利用者(owner / editor / viewer)。運営コンソール(`/super`)は運営者向けのため本書では簡潔に扱う
- 記法: 「推測」と書いたものはコードからの推定で、実機では未確認

## 1. 画面一覧

| ---------- | ------------------ | ----------------------------------------- | ------------------------------------------------------------------------------------- |

### 1.3 運営コンソール(`/super` 配下、運営者向け)

`/super-login`(メール + パスワード + 認証コード)、`/super`(テナント一覧・作成・改名・削除)、`/super/tenants/:id`(メンバー一覧と剥奪、健全性チェック、孤児アセット、再投影)、`/super/users`(検索・BAN)、`/super/modules`、`/super/dlq`、`/super/audit`。

テナント側から見て重要なのは、**メンバー管理がこのコンソールにしか無い**こと(テナント owner が自分でメンバーを招待・変更する画面は無い)。

## 2. ナビゲーション構造

```
/login ─→ /tenants ─→ /t/:slug ──(redirect)──→ コンテンツタイプ一覧
                          │
             サイドバー ──┼─ コンテンツタイプ ─┬─ 新規 / 編集(型定義)
                          │                    └─ 「レコード」リンク ─→ レコード一覧 ─┬─ 新規
                          │                                                         └─ 編集(公開・ステータス・削除)
                          ├─ アセット ─→ 「編集」─→ レコード編集画面(型 = asset)
                          └─ モジュール
```

要点:

- **コンテンツ(記事など)に到達する唯一の経路が「コンテンツタイプ一覧の行内リンク『レコード』」**。サイドバーには型ごとの入口が無い(`nav:item` は `$tenantSlug` 以外のパラメータを持てない契約のため、`packages/ui/src/slots.ts` の `NavItemContribution` コメント参照)
- テナントのトップ(`/t/:slug/`)は型定義画面へリダイレクトする。ログイン直後に最初に見るのが「スキーマ設計画面」
- パンくず・戻るリンク・現在地表示が無い。レコード編集から一覧へ戻る手段はブラウザバックかサイドバー → コンテンツタイプ → レコード の 2 クリック
- 設定系(テナント名、メンバー、公開 API の URL、プロフィール・パスワード変更)の入口が無い

## 3. WordPress との対比

| WordPress の構成要素                                                                       | 役割                                                   | plyrs の現状                                                                                     | ギャップ                                            |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| ダッシュボード                                                                             | ログイン直後の着地点。最近の投稿、下書き、クイック作成 | 無し(型定義一覧へリダイレクト)                                                                   | 着地点が編集者の仕事と無関係                        |
| 投稿 / 固定ページ / カスタム投稿タイプ(左メニューに型ごと)                                 | 「投稿一覧」「新規追加」が型ごとにメニュー化           | 型ごとのメニューが無い。型定義一覧の行内リンクから入る                                           | 最大の迷いどころ。「記事を書く場所」が見つからない  |
| 投稿一覧(すべて / 公開済み / 下書き のタブ、検索、絞り込み、一括操作、ページ送り)          | 大量コンテンツの管理                                   | 更新日時降順の表のみ。ステータス表示は「ワークフロー状態」で、公開済みかどうかは一覧で分からない | 公開状態が見えず、検索もない                        |
| 投稿編集(右サイドバーに「公開」ボックス: 下書き保存 / プレビュー / 公開 / 状態 / 公開日時) | 保存と公開を一か所で扱う                               | 上部ツールバーに「公開」とステータス、本文下に「保存」、右に公開状態パネル、最下部に削除         | 操作が 4 か所に散在。保存と公開の関係が分かりにくい |
| メディアライブラリ(グリッド表示、ドラッグ&ドロップ、詳細パネル)                            | 画像の閲覧・アップロード・代替テキスト編集             | 表形式 + `<input type="file">`。編集は汎用レコード画面へ遷移                                     | 画像中心の閲覧に向かない。単一ファイルのみ          |
| 外観 / プラグイン                                                                          | 機能拡張                                               | 「モジュール」(有効化 / 無効化のみ)                                                              | 概念は近い。説明文や設定画面は無い                  |
| ユーザー                                                                                   | メンバー招待・権限変更                                 | テナント側には無い(運営コンソールのみ)                                                           | owner が自分で人を追加できない                      |
| 設定(一般・パーマリンク等)                                                                 | サイト名、URL などの設定                               | 無い                                                                                             | 公開 API のエンドポイントなどを確認する場所が無い   |
| カスタムフィールド / ACF の「フィールドグループ」                                          | 開発者・サイト設計者向けの型設計                       | 「コンテンツタイプ」がメインメニュー先頭                                                         | 設計者向け機能が編集者向け機能と同列・先頭に並ぶ    |

WordPress との対比では、**「型を定義する場所」と「中身を書く場所」の主従が逆転している**のが構造上の核心。WordPress では投稿タイプはコードやプラグイン(ACF / CPT UI)で定義され、メニュー上は「投稿」「固定ページ」が主役で、フィールド設計は「設定」「ツール」寄りの奥にある。plyrs では型定義が主役で、コンテンツはその下位にぶら下がる。

## 4. 画面ごとの課題

### 4.1 入口(ログイン / サインアップ / テナント選択)

- サインアップ後の行き先が「テナントは運営者が発行します」だけで、次に何をすればよいか分からない
- 所属テナントが 1 件でも毎回テナント選択を経由する
- テナント選択のカードに `slug / role` が素のまま出る(`owner` などの英語ロール名)
- パスワード再設定の導線が無い(推測: API にも該当エンドポイントが無い)

### 4.2 共通シェル

- サイドバーの現在地ハイライトが無い(`activeProps` / `aria-current` の指定なし)
- コンテンツ(型ごとのレコード一覧)への入口が無い
- 同期状態が常時テキストで表示される(「同期: 同期済み」)。正常時にも内部状態を見せており、意味が利用者に伝わりにくい。一方、異常時のバナー(`ConnectionBanner`)はレコード系画面にしか出ない
- 「{テナント名}(テナント切替)」がヘッダー左の小さなリンクで、サイト名表示と切替操作が混ざっている
- ログアウトがヘッダーに直置き。アカウント(プロフィール・パスワード変更)メニューが無い
- パンくずが無い

### 4.3 コンテンツタイプ一覧・編集

- 編集者にとって不要な情報(key / source / version)が一覧の主列に出る
- システム型 `asset` が利用者の型と同列に並ぶ(source=system で区別は付くが説明が無い)
- 「新規」「編集」リンクがロールに関係なく表示される(推測: viewer でも画面には入れ、保存時に API で拒否される)
- フォーム:
  - フィールドの型が `text` `richtext` `relation` などの内部名。WordPress / ACF の「テキスト」「画像」「投稿オブジェクト」のような利用者語彙になっていない
  - フィールドに表示名(ラベル)が無い。key(snake_case)がそのまま入力画面のラベルになる(`record-form.tsx` の `label={field.key}`)。メタモデル側のフィールド定義にも表示名が無い(`packages/metamodel/src/field-types.ts`)
  - `indexed` `unique` `maxLength` `カーディナリティ one/many` が英語・技術用語のまま
  - 関係フィールドの「許可する型」がカンマ区切りの自由入力
  - フィールドの並べ替えができない(追加は末尾、削除のみ)
  - 型の削除手段が無い
- 保存後は一覧へ戻るだけで、続けてコンテンツを作る導線が無い

### 4.4 レコード一覧(投稿一覧に相当)

- 到達経路が深い(2.参照)
- 「ステータス」列はワークフロー状態(下書き / レビュー中 / 公開準備完了 / アーカイブ)で、**公開中かどうかは一覧で分からない**(公開状態は `published_snapshots` が真実源で別管理、design-spec §7)。WordPress 利用者は「公開済み」を状態の一つと期待するので混乱しやすい
- 検索、ステータス別タブ、並べ替え、ページング、一括操作(一括削除・一括公開)が無い
- 更新日時が ISO 文字列そのまま、`version` 列は利用者に意味が無い
- タイトルは「最初の text フィールドの値、無ければ ID 先頭 8 文字」(`lib/record-label.ts`)。タイトルにするフィールドを型側で指定できない
- 同期完了前は「同期中…(状態: connecting)」の 1 行だけが表示される

### 4.5 レコード作成・編集(投稿編集に相当)

- 操作が 4 か所に散在する: 上部ツールバー(公開 / 公開を取り下げ / ステータス)、本文下(保存)、右パネル(公開状態)、最下部(削除)
- **保存と公開が別ボタンで、関係が見えない**。「公開」はサーバーに保存済みの版を公開する(推測: `api/src/do/publish.ts` の `publishRecordCore` は DO 上のレコードを読む)ため、未保存の編集は公開に含まれない。WordPress の「公開 / 更新」1 ボタンに慣れた利用者は、保存せずに公開して変更が反映されないと感じやすい
- 公開中でも「公開」ボタンのラベルが変わらない(再公開の意味になる)
- 「ステータス: 公開準備完了」と「公開」ボタンが別物で、ステータスを変えても公開されない
- 保存成功のフィードバックが無い(`record-form.tsx` の `notice` は競合時のサーバー版採用時のみ)
- 未保存のまま離脱しても警告が無い(`useBlocker` / `beforeunload` の使用なし)
- 新規作成後は一覧に戻る。作成した記事をそのまま公開したい場合、一覧から探し直して開く必要がある
- プレビューが無い
- 公開日時の予約、パーマリンク(slug)専用の UI が無い。公開 API の `records/:type/slug/:slug` は「key が `slug` の unique な text フィールド」という暗黙の規約に依存しており(`apps/api/src/projection/payload.ts` の `promoteSlug`)、画面上ではその規約が分からない
- 削除はゴミ箱ではなく即時削除(2 段階確認のみ)
- 画面幅が狭いときのレイアウト調整が無い(推測)

### 4.6 アセット(メディアライブラリに相当)

- 表形式で画像の一覧性が低い。グリッド表示が無い
- アップロードは素の `<input type="file">`、単一ファイルのみ、ドラッグ&ドロップ無し、進捗表示無し
- 「編集」が汎用レコード編集画面に飛ぶため、公開ボタンやステータスなど、メディアには不要な操作まで表示される(推測: `record-editor:*` スロットは型を区別しない)
- 「未参照のみ表示」の意味(どこからも使われていないファイル)が説明されていない
- 削除確認ダイアログの使用箇所が `型 key / フィールド key — ID 先頭 8 文字` で、どの記事か分からず、リンクも無い

### 4.7 モジュール

- 一覧と有効化 / 無効化のみ。モジュールが何をするかの説明が無い
- 有効化してもナビゲーションに項目が増えるとは限らず、有効化後に何をすればよいか分からない(推測)
- 権限不足時のエラーが「操作に失敗しました(権限を確認してください)」のみ

### 4.8 全体に共通

- 日本語と英語の内部用語が混在(`key` `source` `version` `indexed` `relation` など)
- 「レコード」「コンテンツタイプ」「アセット」は WordPress の「投稿」「投稿タイプ」「メディア」と語彙が異なる。概念は近いので、画面上の呼称を寄せる余地がある
- ロールによる表示の出し分けがほぼ無い(viewer 判定は公開ツールバーとステータス切替の 2 か所のみ)
- 日時のローカライズ(相対時刻・日本語表記)が無い
- 空状態(「まだありません」)に次の行動への導線が無い
- 確認ダイアログの作りが画面ごとに異なる(インラインのボタン切替 / `alertdialog` の div)。モーダルとしての共通部品が無い

## 5. 再構築の方向性

A〜H のすべてを再構築の対象として採用する(2026-10-17 合意)。優先度は着手順の目安で、各案の具体的な設計は次の段階(情報設計の検討)で決める。

### A. ナビゲーションを「コンテンツ中心」に組み替える(優先度: 高)

- サイドバーの最上段に型ごとのメニューを動的に並べる(例: 「お知らせ」「ブログ」…それぞれに「一覧」「新規追加」)。WordPress のカスタム投稿タイプのメニューと同じ構造
- 「メディア」(現アセット)をその下に置く
- 「コンテンツタイプ」は「設定」または「サイト設計」配下に下げる(owner 向け)
- 前提作業: `nav:item` に `params` を持たせる拡張(`slots.ts` のコメントで予告済み)、またはコンテンツ用の専用スロットを設ける

### B. ダッシュボードを新設して着地点にする(優先度: 高)

- `/t/:slug/` をダッシュボードにする。最近編集したもの、自分の下書き、公開待ち(ステータス「公開準備完了」)、未公開の変更があるもの、型ごとの「新規追加」ボタン
- 所属テナントが 1 件ならテナント選択を飛ばして直接ここへ

### C. 編集画面に「公開ボックス」を設ける(優先度: 高)

- 右サイドバーに保存・公開・ステータス・公開状態・削除を集約する(WordPress の「公開」ボックス相当)
- 主ボタンを状態に応じて切り替える: 未公開なら「公開」、公開中なら「更新」(保存 + 再公開)、補助に「下書き保存」
- 「公開」は未保存の変更を保存してから公開する(仕様変更を伴うので要検討)
- 保存成功のトースト、未保存離脱の警告、作成後は編集画面に留まる

### D. 一覧に公開状態とフィルタを入れる(優先度: 中)

- 一覧の状態表示を「公開中 / 公開中(未反映の変更あり)/ 未公開」とワークフロー状態の 2 軸で見せる。WordPress の「すべて / 公開済み / 下書き」タブ相当
- 検索、並べ替え、ページング、一括操作
- 前提作業: 一覧で公開状態を得る手段(現在はレコードごとの `/publication` 取得のみ)

### E. 型設計(コンテンツタイプ)を利用者語彙に寄せる(優先度: 中)

- フィールドに表示名(ラベル)と説明文を持たせる(メタモデルの変更を伴う)
- 型の選択肢を「テキスト(1 行)」「リッチテキスト」「数値」「日時」「選択肢」「画像・ファイル」「他のコンテンツへの参照」のように言い換える
- タイトル用フィールドの指定、並べ替え、型の削除
- key は表示名から自動生成し、詳細設定に折りたたむ

### F. メディアライブラリを専用 UI にする(優先度: 中)

- グリッド表示、ドラッグ&ドロップ・複数アップロード、詳細はモーダルかサイドパネルで編集(汎用レコード画面に飛ばさない)
- 使用箇所はレコードのタイトルとリンクで示す

### G. テナント設定を新設する(優先度: 中〜低)

- 一般(テナント名、公開 API のベース URL の表示)、メンバー(招待・ロール変更。API 追加が必要)、モジュール(現在の画面をここへ移す)
- アカウントメニュー(プロフィール、パスワード変更、ログアウト、テナント切替)をヘッダー右上に集約

### H. 共通の表層を整える(優先度: 中、A〜G と並行)

- 現在地ハイライト、パンくず、ページ見出しと主操作ボタンの定位置化
- 日時の日本語表記、内部用語(version / source / key)を主表示から外す
- 同期状態は正常時は目立たないアイコンにし、異常時のみバナーを全画面共通で出す

## 6. 決定事項と未決事項

### 6.1 決定事項

#### 画面上の呼称(2026-10-17 決定)

- 総称は「コンテンツ」を使い、WordPress の「投稿」には寄せない。plyrs のコンテンツタイプは記事に限らず、モジュールの型(例: 予約モジュールの `booking.resource` `booking.slot` `booking.reservation`、`apps/api/src/modules/booking/manifest.ts`)も同じ仕組みで扱うため、「投稿」では範囲を連想しにくい
- 利用者の目に入る呼び方は各コンテンツタイプの名前を主にする。サイドバー(案 A)には「お知らせ」「ブログ」「予約」のように型名を並べ、総称の「コンテンツ」は型を設計する設定画面などに限る
- 「レコード」は画面上の呼称から外し、「お知らせの一覧」「お知らせを追加」のように型名で呼ぶ
- 「アセット」は「メディア」に改める。アップロードは画像に限らず任意の形式を受け付ける(`apps/api/src/routes/tenant.ts`)ため、同じ範囲を扱う WordPress のメディアライブラリと呼称を揃える
- 内部の識別子(`asset` 型、API パス、コード上の名前)は変更しない。画面上の表示だけの方針とする

#### 案 C: 編集画面の公開ボックス(2026-10-17 決定)

- 5 章の案 C の内容をすべて採用する。「公開」は未保存の変更を保存してから公開する。これは管理画面側の処理の順序だけで実現でき、API の変更は伴わない
- 具体設計は [案 C: 編集画面の公開ボックス 設計](./c-publish-box.md) にまとめる
