# 用語集

plyrs のドキュメント、コード中のコメント、画面の文言で使う語の正本。新しい文章はこの用語集に従う。初めて読む人が、設計書や過去の計画書に出てくる語を引けることも目的にしている。

節の構成は次のとおり。

1. 新しい用語と意味 — 今使う語と、その意味
2. 旧語との対応 — 過去の文書やコードに残る旧い語から、新しい語を引く表
3. コード識別子との対応 — 用語とコード上の名前の対応

## 1. 新しい用語と意味

### 公開用 DB

公開配信 API が読む、全テナント共有の D1。バインディング名は `PROJECTION_DB`。各行に `tenant_id` が付き、公開版から作られた読み取り専用のデータだけを持つ。公開の読み取り経路(`/public/v1/:tenantSlug/...`)は Durable Object を起こさず、この DB とキャッシュだけを読む。

公開用 DB は派生物であり、正本ではない。正本はテナントの Durable Object にある公開版で、公開用 DB はそこから作り直せる。主なテーブルは `projected_records`、`projected_relations`、`projection_tombstones`。

公開用 DB へ反映するのは、record を publish / unpublish した時点である。Durable Object の outbox から反映ジョブがキューに載り、consumer が冪等に書き込む。

### 公開版(スナップショット)

record を publish した瞬間の姿を、Durable Object 内の `published_snapshots` に保存したもの。編集中の `records` とは別の行として持つ。そのため、編集を続けても、publish し直すまで公開される内容は変わらない。

公開されているかどうかは、`published_snapshots` の行があるかどうかで決まる。publish が行を作り、unpublish が行を消す。公開用 DB はこの公開版から作られる。

文中で公開版の写しを指す場合は「スナップショット」と書く。

### 公開用 DB の再構築

あるテナントの公開用 DB の行を、公開版から作り直す運用。反映ジョブの取りこぼしや不整合を直すために開始する。テナントのオーナーが API から、または super 管理者が運営管理画面から開始できる(権限は `projection:rebuild`)。

流れは次のとおり。

1. 開始時に基準時刻(epoch)を記録する。
2. テナントの公開版をページ単位で読み、公開用 DB へ書き込み直す。ページごとに、次のジョブを自分で送る。
3. 最後に、基準時刻より前に書かれた行を削除する。公開版から消えたのに公開用 DB に残った行(残骸の行)が、ここで取り除かれる。

この処理は、同時に動く通常の publish / unpublish の反映と競合しても整合を保つように作られている。反映ジョブ側の順序ガードは `publish_seq` と `projection_tombstones` による。

「再構築」だけの略記は、同じ段落で「公開用 DB の」と明示した後に限る。`docs/admin-ux` にある「管理画面 UX 再構築」は別の話である。

Durable Object 内で、record から relations の行を作り直す処理は、公開用 DB の再構築とは別のものである。この場合は「relations 行の作り直し」と書く。

### 管理画面と運営管理画面

- **管理画面**: テナントの利用者が、コンテンツと自テナントのユーザーを管理する画面。`apps/admin`。
- **運営管理画面**: 運営者が、全テナントと super 管理者を管理する画面。管理画面の中に同居する。API は `/super/v1/*`、認証は `/super-auth/*`。

運営管理画面を「管理画面」と略さない。「管理画面」はテナント向けの画面だけを指す。

### super 管理者

運営者のアカウント。テナントに属さず、運営管理画面にログインして全テナントを管理する。コントロールプレーン D1 の `super_admins` に保存され、パスワードと TOTP で認証する。最初の 1 人は、デプロイ直後に `/super-auth/bootstrap` で作る(手順は `docs/deploy.md`)。設計書の「特権テナント(運営者)」に対応する。

### エージェント接続(MCP)の用語

設計書の第 16 章で使う語。MCP は Model Context Protocol の略で、AI エージェントが外部のツールを呼ぶための規約。plyrs では管理画面の操作をエージェントから行うための第三の経路として導入する。

| 用語 | 意味 |
| --- | --- |
| 操作カタログ | record や型に対する操作(作成・更新・公開など)の名前、入出力のスキーマ、必要な権限、説明文、提供する経路を 1 か所で宣言したもの。MCP のツール、REST、CLI はここから生成する。Durable Object への RPC は `invoke(op, input)` の 1 本に集約する |
| 変更履歴 | record の版の記録。Durable Object 内の履歴表に、表自身の連番をキーとして保存し(`records.version` は属性。publish の版は `source_version` で識別)、誰が(actor)どの経路から(via)変えたかを持つ。管理画面の「履歴」画面と、エージェントの `record_history` / `record_restore` が読む。運営操作の `audit_logs` とは別物 |
| 提案(change set) | エージェントの変更を record へ直接書かず、採用・却下を待つ形で保存したもの。管理画面で差分を見て人が判断する。`record:propose` スコープだけを持つトークンの変更は提案になる。公開状態・ワークフロー状態に加わる 3 本目の軸 |
| スコープ | トークンに付く権限の範囲。名前は Durable Object の `Operation`(`record:read`、`record:write`、`record:publish` など)と同じ。実効権限はスコープとロールの共通部分で、スコープは権限を絞るだけで増やさない |
| PAT | Personal Access Token。管理画面で所有者が発行する長命の Bearer トークン。ヘッダにトークンを貼れるクライアント(Claude Code、CI など)が MCP に接続するための正式な経路の 1 つ。D1 にはハッシュだけを保存する |
| 判定モード(strict) | 同期の競合判定の厳しさ。管理画面の経路は現行どおり(別フィールドはマージ、同一スカラーは後勝ち、同一リッチテキストは競合)。エージェントの経路は strict で、変更したフィールドのどれか 1 つでも版が違えばスカラーも競合にする |
| 経路(via) | 書き込みがどこから来たか。管理画面の同期、MCP、REST の 3 つ。操作カタログの提供先、変更履歴の記録、判定モードの選択で共通に使う |
| 限定公開 | 読み取り専用 MCP を production に出す際の条件。告知しない、PAT の発行は所有者のみ、ツール名・返り値・PAT の形式は書き込み MCP の公開まで変えうる(後方互換の約束なし) |

### その他の用語

| 用語 | 意味 |
| --- | --- |
| 正本(source of truth) | 唯一の正しい元データ。他のデータはここから作り直せる。例: 公開版は公開用 DB の正本 |
| 決定 | 設計書の決定ログに載った判断。`決定 10` のように番号で参照する |
| 判定する | 同期の競合で、どちらの値を採るかを決めること |
| 引き継ぎ事項 | あるフェーズの作業から次へ渡す、残課題と注意点 |
| 画面の「失敗したジョブ」 | 運営管理画面で、キューの処理に失敗して退避されたジョブを一覧する項目 |
| 画面の「レコードのないファイル」 | 運営管理画面で、どの record からも参照されていないアセットを一覧する項目 |
| 画面の「検索」 | 運営管理画面のテナント詳細で、どの record からも参照されていないアセットを調べる操作(「レコードのないファイルを検索」)。旧称は「走査」 |
| 画面の「メンバーから外す」 | テナントのメンバーの権限を取り消す操作 |

## 2. 旧語との対応

過去の計画書(`docs/superpowers/plans/`)は実施時点の語のまま残している。そこに出てくる旧語は、この表で新しい語に読み替える。

### 2.1 Issue で決定済みの語

| 旧語 | 新しい語 | 補足 |
| --- | --- | --- |
| 墓標 | `projection_tombstones`(の行) | 訳語を付けない |
| 投影 D1、公開投影 D1、共有投影 | 公開用 DB | 初出で `PROJECTION_DB` を添える |
| 投影する、投影更新 | 公開用 DB へ反映する、反映 | |
| 投影行、投影ジョブ、投影ペイロード | 公開用 DB の行、反映ジョブ、反映用ペイロード | |
| records 投影、relations 投影 | `projected_records`、`projected_relations` | テーブルを指す場合 |
| 再投影(ジョブ) | 公開用 DB の再構築(ジョブ) | relations 行の張り直しを指す「再投影」は「relations 行の作り直し」 |
| 凍結 embed、凍結埋め込み、凍結 URL | アセットの埋め込み情報、埋め込み URL | |
| 凍結投影 | 公開版に保存 | 例: `apps/api/src/do/publish.ts` |
| 写し(公開版を指すもの) | スナップショット | |
| 裁定(名詞) | 決定 | 過去の計画書の `裁定 N` は、コードのコメントの `決定 N` と同じもの。番号は変わらない |
| 裁定する、裁く(競合) | 判定する | `docs/design-spec.md` §10 |
| 運営コンソール、特権コンソール、管理コンソール | 運営管理画面 | テナント向けの「管理画面」とは別 |

### 2.3 変えない語

次の語は、一般的であるか設計書の定義語なので、そのまま使う。

- 持ち越し
- 見送り
- 論点(`論点W` のように記号として参照される)
- 第1段、第2段
- 冪等
- シェル
- パンくず
- 確認待ち

## 3. コード識別子との対応

用語を変えても、コード上の名前は変えない。次の名前はそのまま残る。

| 用語 | コード上の名前 |
| --- | --- |
| 公開用 DB | バインディング `PROJECTION_DB`、スキーマ `packages/db/src/projection.ts`、マイグレーション `packages/db/drizzle-projection/` |
| 公開用 DB の行 | テーブル `projected_records`、`projected_relations` |
| 墓標 | テーブル `projection_tombstones` |
| 公開用 DB への反映 | キュー `PROJECTION_QUEUE`、実装 `apps/api/src/projection/`(`consumer.ts`、`jobs.ts`、`payload.ts`) |
| 公開用 DB の再構築 | ジョブ `jobType: "reproject"`、Durable Object のメソッド `startReprojection`、API `/v1/t/:tenantId/reproject`(テナントのオーナー)と `/super/v1/tenants/:tenantId/reproject`(super 管理者)、監査アクション `reproject.start` |
| 公開版 | テーブル `published_snapshots` |
| 順序の基準 | 列 `publish_seq` |
| 運営管理画面 | API `/super/v1/*`、`/super-auth/*` |
| super 管理者 | テーブル `super_admins`、`super_sessions` |
| 失敗したジョブ | テーブル `dead_letters`、DLQ(キュー名が `-dlq` で終わるもの) |
| 決定 N | 過去の計画書の `裁定 N` と同じ番号 |
