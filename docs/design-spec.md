## 0. 目的とスコープ

理想的な Web システムを自作するための、マルチテナント SaaS。初期段階は一般的なブログ的 CMS だが、内部は kintone 的な「型をデータとして定義する」BaaS 構造を土台に持ち、将来のプラグイン（予約・メール配信等）を無理なく載せられることを狙う。

### 中核の設計原則

- **ローカルファースト最優先**: 編集体験は tanstack-query / tanstack-db によるローカルファースト同期で駆動する。パフォーマンスの主軸。
- **コンテンツ構造の方針 + 実行時定義の自由の両立**: 『Designing Connected Content』の「型付き・連結・再利用可能」という設計方針を、kintone 的な「ユーザー/プラグインが実行時に型を定義する」メカニズムの上で実現する。両者は対立せず、後者のメタモデルを前者の方針で設計する。
- **固定管理画面 + ヘッドレス公開**: 管理画面（バックエンド）は固定 UI を提供する。一方、公開側フロントエンドはヘッドレスで、公開コンテンツ配信 API を介して自由に構築できる（Contentful 型）。
- **Cloudflare 前提**: ホストは Workers、データは Durable Objects (SQLite backend)、バイナリは R2。

## 1. テナント構造（二層）

```
特権テナント（運営者＝自分）
  └─ テナント（利用者） = 1 CMS = 1 Durable Object (SQLite)
```

- **特権テナント**: 全テナントと管理者アカウントの管理を行う。
- **テナント**: CMS を運用し、コンテンツと自テナントに属するユーザーアカウントを管理する。
- **下位区切りは持たない**（当初案の「ワークスペース」層は廃止）。1テナントが複数サイトを必要とする事態が生じたら、その時点でコンテンツ型/関係で表現するか再検討する。

> 注: 当初の三層構造（特権 → 管理者テナント → ワークスペース）および「ユーザー↔ワークスペースの多対多メンバーシップ」は、実課題に照らして不要と判断し廃止した。

## 2. データ分離戦略

### コントロールプレーン / データプレーンの分離

システムは性質の異なる2種類のデータを持ち、これを分離することが構造上の背骨である。

- **コントロールプレーン（ID・認可）**: テナント、ユーザー、メンバーシップ、ロール、課金。認可はワークスペース（テナントのデータ本体）の**外側**に置き、リクエストの入口で必ず検証するゲートとする。「テナントのデータを開いてよいか」を、そのデータを開かずに判定できる必要があるため。
  - メンバーシップは二層化により `(user_id, tenant_id, role)` の素直な形。多対多の交差判定は存在しない。
- **データプレーン（コンテンツ）**: 各テナントの CMS 実体。テナントごとに物理分離する（下記）。

### テナント = 1 Durable Object (SQLite)

- 1テナント = 1つの DO-SQLite。**DO 境界がテナント境界**であるため、コンテンツ系テーブルに `tenant_id` 列は不要で、全クエリからテナント絞り込みが消える。
- 「決して他テナントのデータにアクセスできない」を、論理（全クエリの正しさ）ではなく**物理（データが別 DB に存在しない）**で保証する多層防御。
- DO は各テナントの唯一の書き込み権威（single-writer）であり、ローカルファースト同期のハブとなる。

### 認可フロー

```
クライアント → Worker（認証・メンバーシップ検証） → 該当テナントの DO へルーティング → 同期
```

信頼境界は Worker に固定する。ヘッドレスで API を公開するため、クライアント側の権限申告は一切信用しない。

## 3. インフラとコスト構造

### 採用プリミティブ

- **Workers**: 実行層・認可ゲート・API。
- **Durable Objects (SQLite backend)**: テナントごとのデータ本体 + 同期ハブ。GA 済み、1オブジェクト 10GB。
- **D1**: コントロールプレーン（ID・membership・セッション正本）＋公開読み取りモデル（テナントごとの公開版から作る公開用 DB。第12章）。スケール・トゥ・ゼロ、読み取りレプリカ。
- **Cloudflare Queues**: 非同期副作用フックの搬送（第9章）。
- **R2**: アセットのバイナリ。
- **キャッシュ / KV**: 公開配信の read パス前段、ブロックリスト等。

### コストの要点

DO の課金は「リクエスト / Duration（実行時間）/ ストレージ」の3種だが、実質的に支配的なのは **Duration** のみ。そして Duration は**ハイバネーション（休眠）できているか**で桁が変わる（公式試算で、同規模でもハイバネなし $138/月 → ハイバネあり $10/月）。CMS はワークスペースが大半の時間アイドルで、ストレージも小さいため、条件を満たせば実質 Workers 有料プラン下限（$5/月）に張り付く。

### コストが強制する設計制約（確定事項）

1. **同期接続は WebSocket Hibernation API 前提**（Hibernation API を使わない `accept()` は接続時間まるごと課金になるため禁止）。
2. **公開 read パスは DO を経由しない**（キャッシュ / R2 / レプリカに分離。一般閲覧で書き込み権威の DO を起こさない）。

> この2点目が、後述する「非対称二経路」の物理的な根拠になる。

> **コスト攻撃面の注記**: モジュールが公開する無認証 write（第9.7章）は「認証なしで DO を起こせる唯一の経路」であり、ハイバネーション前提を破壊しうる**コスト DoS の攻撃面**である。防御は DO 到達**前**の Worker 層（Turnstile 等の検証＋レート制限）で行い、認可の第1段（第11.5章）と同じ位置で落とす。詳細は第9.7・11.7章。

## 4. メタモデル（型をデータとして持つ）

固定した型でも、生の SQL スキーマをユーザーに開放するのでもなく、**制約付きメタモデル**を採用する。

- 型付きフィールドの**パレットはプラットフォームが固定**する（第5章）。
- **型の定義（＝どのフィールドを組み合わせるか）は、ユーザーもプラグインも実行時に data として作成できる**。

これにより、kintone 的な実行時の自由度、Connected Content 的な構造方針、tanstack-db の型付きコレクション（レジストリから実行時にスキーマ生成）、プラグインの安定契約が同時に成立する。

> プラグインが必要とするのは「拡張性」であって「エンドユーザーによる任意スキーマ定義」ではない（WordPress の実例）。拡張は (1) メタモデルでの型合成、(2) プラグイン専用テーブルという脱出ハッチ、で賄える。

### 4.1 型キーの名前空間

`content_types.key` は UNIQUE だが、**ユーザー型とプラグイン型が同一キー空間を共有すると衝突する**（予約モジュールの `booking` とユーザー作成の `booking` 等）。規約:

- **プラグイン所有型はモジュールIDで名前空間化**する（例: `booking.slot`, `booking.reservation`）。
- ユーザー型は接頭辞なしの名前空間（または `user.` 接頭辞）に置く。
- 登録時に名前空間規約を強制し、越境登録を拒否する。

### 4.2 スキーマ寛容性と型定義マイグレーション

JSON 格納（スキーマレス）である以上、**「古い形の `data` が残り続ける」のが常態**。型定義が変わっても既存 records は自動追従しない。原則:

- **読み取りは寛容（tolerant read）**: 欠損フィールドは既定値/不在として扱い、未知フィールドは無視（ただし破棄せず保持）。records が最新の型定義に適合している保証はない、を前提に読む。
- **書き込みは現行定義で検証（validate-on-write）**: 書き込み時点の型定義でバリデーションし、その record だけが現行形に更新される（遅延マイグレーション）。
- **既定で一括変換しない**。フィールドの追加/削除/required化/型変更/renameは、上記の遅延マイグレーションで吸収する。rename は「remove + add」の破壊的変更として扱い、値を保持したいなら明示的な移行マッピングを伴わせる。

**プラグイン型の再配布（運用問題）**: `content_types` は各テナント DO 内にあるため、**モジュールのバージョンアップ＝有効化中の全テナント DO への型定義再配布**になる。編成:

- モジュールは**バージョン付きの型定義マニフェスト**を持つ。
- モジュール更新時、コントロールプレーンが有効化テナントごとに**マイグレーションジョブを Queues で配信**し、各テナント DO の `content_types` を更新する。
- マイグレーションは**冪等かつバージョン管理**。データ適合は上記の遅延マイグレーションに委ね、DDL を伴う一括変換は避ける。

## 5. フィールド型パレット

### 設計原則: 2層に分ける

- **基底型（storage 層・小さく閉じる）**: SQLite に実際に格納されるもの。
- **フィールド型（authoring 層）**: 基底型 + バリデーション + UI + 意味。ユーザー/プラグインはこちらを見る。

email・URL・slug・通貨・評価スター等は独立した型にせず、基底型 + 制約 + UI ヒントで導出する（モデルと格納・表現の分離）。

### スカラー基底型（この5つに閉じる）

`text` / `number` / `boolean` / `datetime` / `json`

- **通貨は必ず整数の最小単位**で持つ（SQLite REAL の浮動小数誤差を避ける）。
- **datetime は UTC の ISO8601（またはエポック）**で格納し、タイムゾーンは表示層で扱う。
- **json は脱出ハッチ**。中身は関係もクエリも使えない不透明な塊になるため濫用しない。「関係で表せるものを json に押し込む」ことは禁止。

### 構造型

- **enum / select（単一・複数）**: 選択肢は型定義の一部として持つ。
- **リッチテキスト**: **構造化（JSON AST）**を採用（論点A）。本文中のリンクや埋め込みメディアを参照として第一級に持つ。プレーン Markdown ではない。
- **media / asset**: **アセットは独立コンテンツ型**（論点E）。実体は R2 のオブジェクト + メタデータ行。「メディアフィールド」は独立型ではなく `allowedTypes=[asset]` の**関係フィールド**にすぎない。alt / caption は**アセット内在**（文脈依存にはしない）。
- **入れ子コンポーネント / repeater**: **認めない**（論点B、初期段階）。「構造化した小要素の繰り返し」は入れ子ではなく**独立コンテンツ型 + 多対多関係**で表す。

### 関係型（心臓部）

確定した設計:

- **参照であって埋め込みではない**（正規化）。単一の正本を指す。埋め込みコピーは禁止。
- **カーディナリティは 1対1 / 1対多 / 多対多をサポート**。
- **双方向は片側のみ格納し、逆側は live query の join で合成**（逆リンクを二重保存しない）。
- **「属性を持つ関係」は専用機構を作らず、関係フィールドを持つコンテンツ型として reify する**。例: 予約(booking) = Resource / Customer / 時間枠への関係フィールド + 自身のスカラー（状態・人数）を持つ1コンテンツ型。予約プラグインは新機構を要求せず既存プリミティブの合成で成立する。
- **多態（論点C）**: 指し先を1型に固定せず、**許可された型の集合（allowedTypes）を宣言できる**。プラグインが既存の任意型に接続できる。
- **参照整合性（論点D）**: DB の FK 制約ではなく**ソフト参照**。dangling を許容し、クエリ時に解決する。

### ローカルファーストが強制する帰結（確定）

1. **ID はクライアント生成（ULID/UUID）**。未同期の相手への関係を楽観的に張るために必須。
2. **ソフト参照前提**（上記D）。同期途中の一時的 dangling を正常系として扱う。

### システムフィールド（全型に無償付与）

`id` / `createdAt` / `updatedAt` / `createdBy` / `updatedBy` / `status` / `version`

### フィールド制約は宣言ベース（indexed / unique）

索引や一意性はコードのアドホックな扱いにせず、**型定義の `config` に宣言**する。`"indexed": true`（論点J）に加え、**`"unique": true`** を持てる。

- **一意制約の必要性**: 例えば slug は公開 API の単体取得キー（第12.4章）であり、一意でなければならない。しかし値は `data` JSON 内にあり SQLite の UNIQUE を直接張れない。
- **強制の実装**: (a) DO の書き込み経路で**システム定義 `beforeWrite` フック**として一意性を検証する（第11.5章の認可と同じフック機構に乗る＝一貫性）。(b) 必要なら generated column ＋ UNIQUE index で DB レベルにも張る。
- `indexed` / `unique` はいずれも「制約や最適化を宣言としてデータで持つ」思想で揃い、DO 索引・公開用 DB のカラム（第12章）・一意検証を一元的に規定する。

## 6. 物理表現（DO-SQLite 内: コンテンツ中核3テーブル + 運用テーブル群）

DO-SQLite にはコンテンツの中核3テーブル（本章）に加え、章をまたいで定義される運用テーブル群が同居する（末尾 6.x に一覧）。まず中核3テーブルを述べる。

物理表現の三択（table-per-type / 汎用 records+JSON / EAV）のうち、**汎用 records + JSON + generated column を基軸**とし、**関係だけ正規化テーブルに分離**するハイブリッドを採用する。

- table-per-type: 実行時 DDL がワークスペースごとにスキーマ版数を分裂させ、メタモデルと二重管理になるため不採用。
- EAV: 1レコード復元に自己 join の山が要り、tanstack-db の typed collection と壊滅的に相性が悪いため却下。

以下は**1テナント DO-SQLite の中身**（`tenant_id` 列が無いのは DO 境界がテナント境界のため）。

### content_types（型定義をデータとして持つ）

```sql
CREATE TABLE content_types (
  id            TEXT PRIMARY KEY,        -- ULID
  key           TEXT NOT NULL UNIQUE,    -- 'article', 'author', 'booking' 等の機械名
  name          TEXT NOT NULL,           -- 表示名
  fields        TEXT NOT NULL,           -- JSON: フィールド定義の配列
  source        TEXT NOT NULL DEFAULT 'user',  -- 'user' | 'plugin' | 'system'
  plugin_id     TEXT,                    -- source='plugin' のとき所有プラグイン
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  version       INTEGER NOT NULL DEFAULT 1
);
```

`fields` のフィールド定義例（関係フィールド）:

```json
{
  "key": "author",
  "type": "relation",
  "required": true,
  "config": {
    "allowedTypes": ["author"],
    "cardinality": "many",
    "ordered": true,
    "snapshotEmbed": "id"
  }
}
```

- フィールド追加 = この JSON 配列への要素追加 = **DDL ゼロ**。
- `source` / `plugin_id` はプラグイン所有型を同機構で登録するための伏線。

### records（全コンテンツの実体）

```sql
CREATE TABLE records (
  id             TEXT PRIMARY KEY,        -- ULID（クライアント生成）
  type           TEXT NOT NULL,           -- content_types.key を参照（ソフト）
  data           TEXT NOT NULL,           -- JSON: スカラー・enum・リッチテキストAST のみ
  field_versions TEXT NOT NULL DEFAULT '{}',  -- JSON: {fieldKey: counter}。フィールド単位競合検知用（第10章）
  status         TEXT NOT NULL DEFAULT 'draft',  -- ワークフロー専用: draft|in_review|ready|archived（publishedは持たない）
  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL,
  created_by     TEXT NOT NULL,
  updated_by     TEXT NOT NULL,
  version        INTEGER NOT NULL DEFAULT 1  -- record 全体の単調カウンタ
);

CREATE INDEX idx_records_type ON records(type);
CREATE INDEX idx_records_type_status ON records(type, status);
```

**version の規則（第10章の同期と整合）**:

- `version`（record 全体）: DO が**受理したあらゆる書き込みで +1**。用途は publish 陳腐化検知（第7章の `source_version` 比較）＝「公開後に編集されたか」の粗い判定。
- `field_versions`（フィールド単位）: DO が**そのフィールドを書いたときにそのキーの counter を +1**。用途は同期の競合検知（第10章）。関係フィールドも物理的には `relations` に書き出されるが、競合検知の対象としてこのマップにキーを持つ（値の格納場所と競合検知は別レイヤー）。
- 両者は DO（single-writer）が書き込み受理時に原子的に更新する。クライアントは各フィールドの最後に同期した `field_versions` を保持し、書き込み時に base version を添えて競合判定に供する。

- system フィールドは実カラム。型固有フィールドのみ `data` JSON に格納。
- **関係は `data` に入れない**（relations テーブルへ）。`data` はスカラー・enum・リッチテキスト AST のみ。
- ホットフィールドは generated column + expression index で専用カラムへ切り出す。**切り出しは宣言ベース**（論点J）: 型定義の `config` に `"indexed": true` を持つフィールドについてのみ、型定義時に一度だけ generated column を張る。自動索引（全 datetime/number）や使用パターン推定は採らない——型が無制限に増える以上、索引の無制限増殖を防ぐため。

```sql
ALTER TABLE records ADD COLUMN g_published_at TEXT
  GENERATED ALWAYS AS (json_extract(data, '$.published_at')) VIRTUAL;
CREATE INDEX idx_records_published_at ON records(g_published_at);
```

- 索引宣言の後付け変更は、型定義の version 更新に伴う軽い DDL として扱う（追加＝generated column 追加で既存行を書き換えない／削除＝drop）。型定義のマイグレーション経路で同時に適用でき、新機構は不要。

### relations（関係 + 参照インデックスを兼ねる）

```sql
CREATE TABLE relations (
  id            TEXT PRIMARY KEY,        -- ULID
  source_id     TEXT NOT NULL,           -- 参照元 record
  source_field  TEXT NOT NULL,           -- 由来フィールド（本文由来は 'body' 等）
  target_type   TEXT NOT NULL,           -- 多態タプルの型側
  target_id     TEXT NOT NULL,           -- 多態タプルのID側（存在は保証しない＝ソフト）
  ordinal       INTEGER NOT NULL DEFAULT 0,
  origin        TEXT NOT NULL DEFAULT 'field'  -- 'field' | 'body'
);

CREATE INDEX idx_relations_source ON relations(source_id, source_field);
CREATE INDEX idx_relations_target ON relations(target_id);
CREATE INDEX idx_relations_target_type ON relations(target_type, target_id);
```

この1枚が、参照インデックスを別物を作らず兼ねる。有効な問い:

- 順引き（この記事の著者は誰か）: `idx_relations_source`
- 逆引き（この著者を参照する記事は）: `idx_relations_target`
- orphan 検出（どこからも参照されないアセット）
- 安全な削除前の使用箇所表示（ソフト参照でカスケードしないため必須）
- 本文中リンクの一元化: リッチテキスト保存時に AST から参照を抽出し `origin='body'` で同じ表に書き出す

**運用規約**: relations は `data` / AST から導出される**派生データ**。正本は record 側。record を書くたびに該当 `source_id` + `source_field` の relations 行を消して張り直す（relations 行の作り直し）。DO の single-writer 性により relations 行の更新に競合が起きない。

### 6.x DO-SQLite 内テーブルの全体像

中核3テーブルに加え、各テナント DO には以下が同居する（章をまたいで定義）。この一覧が「1つの DO の中身」の完全な見取り図:

- **中核（本章）**: `content_types` / `records` / `relations`
- **公開版（第7章）**: `published_snapshots`
- **アウトボックス（第12.3章）**: `outbox` — 反映ジョブの原子的記録と送出保証
- **alarm レジストリ（第9.6章）**: `(module_id, next_fire_at)` — 単一 alarm の多重化。sweeper もここに登録する
- **有効化レジストリ（第9.5・11.5章）**: 有効モジュールID / 適用済みマニフェスト version / モジュール権限展開表

## 7. ドラフト / 公開モデル（論点G）

record 層に「編集中の姿」と「公開されている姿」が同居しうる問題を、**record は1行のまま、公開版だけ別テーブルに退避**する方式で解く。

### published_snapshots

```sql
CREATE TABLE published_snapshots (
  record_id      TEXT PRIMARY KEY,   -- records.id と1対1
  type           TEXT NOT NULL,
  data           TEXT NOT NULL,      -- publish 時点の data のコピー
  relations      TEXT NOT NULL,      -- publish 時点の関係のスナップショット（JSON）
  published_at   TEXT NOT NULL,
  published_by   TEXT NOT NULL,
  source_version INTEGER NOT NULL    -- どの records.version を publish したか
);
```

- **records = 編集の正本（＝ローカルファースト同期の対象）**。編集者はここを楽観的に書き続ける。
- **publish アクション = 現在の records の姿を published_snapshots にコピーする瞬間**。
- **公開配信 API が読むのは published_snapshots のみ**。編集中の records は決して公開経路に出ない。

### 公開状態の正本とワークフロー状態の分離（論点M）

「一つの事実は一箇所」の原則により、公開状態とワークフロー状態を別の正本に分ける。

- **公開状態の正本 = `published_snapshots` 行の存在**。「公開されているか？」は常に snapshot の有無で答える。`records` 側に公開フラグを持たせない。publish が snapshot を作り、unpublish が消す。
- **`records.status` は編集ワークフロー専用**（`draft` / `in_review` / `ready` / `archived` の固定4値）。`published` という値は持たない。
- この分離により「公開軸」と「ワークフロー軸」が直交し、「公開中かつ編集中ドラフトあり」「未公開ドラフト」「取り下げ済みアーカイブ」等が2軸の組み合わせで自然に表現できる。「status=published なのに snapshot が無い」という不整合状態は、そもそも表現できなくなる。

**「未公開の変更があるか」の導出**（新カラム不要、既存の version 比較で出す）:

- `snapshot なし` → 未公開
- `snapshot あり` かつ `records.version == snapshot.source_version` → 公開済み・未編集（クリーン）
- `snapshot あり` かつ `records.version > snapshot.source_version` → 公開済み・未公開の変更あり（要再 publish）

### 上流決定との整合

- relations は records に対してだけ維持され続ける（F 不変、参照グラフは常に一つ）。公開版の関係は snapshot 内に保存する。
- 同期は records、配信は snapshots。経路が物理テーブルで分離。
- records をいくら書き換えても snapshot は publish するまで動かない（編集中も公開版が安定）。

### キャッシュ無効化（論点 I の残件を同時解決）

- **publish がキャッシュ無効化の唯一のトリガー**。
- 通常の編集（drafts の同期）は公開経路に影響せず、キャッシュを触らない。
- publish 時、DO は snapshot を**公開配信レイヤーへ write-through**する（第12章）。これにより一覧・単体クエリの**正確性は公開用 DB の更新で自動担保**される。
- 無効化の粒度は**単体 + 一覧の両方**: 当該コンテンツの単体キャッシュに加え、その record が参加する**一覧（型別リスト等）のキャッシュ**も対象。一覧の正確性は公開用 DB の更新で保たれるため、エッジキャッシュ側は短 TTL（陳腐化を有界化）またはキー単位パージで足りる。
- unpublish は公開用 DB の行の削除 + キャッシュ削除で対称に扱う。

> 公開 read の物理設計（反映先・クエリで指定できる値・一覧インデックス）は独立章として第12章に定義する。

### 公開版の関係の展開（論点K・L）: ハイブリッド

- **基本は参照ID のみ保存する (a)**。加えて**不変・準不変の軽い値だけ選択的に埋め込む (b)**。
- 埋め込み可否の線引きは「フィールドの更新頻度と正確性要求」で引き、型定義の関係フィールド `config` に `"snapshotEmbed": "id" | "value"` として宣言的に持たせる。
- **埋め込んでよい (value)**: アセット配信URL・画像寸法・alt テキスト等（実質不変）。
- **参照IDのみ (id)**: 著者の表示名・肩書き・カテゴリ名等（更新の反映が要る）。
- 陳腐化対策は **L1 + L2**: 埋め込むのは不変値だけという方針（L1）+ 古くなったら再 publish で直す（L2）。共有実体の変更を、それを埋め込んでいる公開版へ自動で連鎖させること（L3）は、実運用で痛みが出てから後付けする。

### archive と公開状態の関係

2軸直交（第「公開状態の正本」節）ゆえ「`status=archived` かつ snapshot あり（＝公開され続ける）」は**合法だが通常は非意図**。軸を結合させない方針を保ち、**archive 時に unpublish を強制しない**。代わりに:

- archive 操作時に「まだ公開中である」ことを**強く警告**し、unpublish を促す。
- 「archived かつ公開中」の record を**健全性チェックで一覧化**できるようにする。

（強制 unpublish は2軸の直交性を壊すため採らない。**確定**: 警告 + 健全性チェックに留める。）

## 8. 非対称二経路（アーキテクチャ要約）

システムには物理的に分離した2つの経路が存在する。

- **書き込み経路（管理）**: 固定管理画面 → tanstack-db → テナントの DO-SQLite に WebSocket（Hibernation）同期。ローカルファースト。認証済み編集者のみが DO を起こす。正本は `records`。
- **読み取り経路（公開）**: 第三者ヘッドレスフロント（Astro / Next 等）→ 公開配信 API → **公開配信レイヤー**（DO から publish 時に write-through された派生読み取りモデル。第12章）から配信。**DO を起こさない**。`published_snapshots`（DO 内）は正本だが公開経路が直接読むことはなく、公開用 DB を読む。

> `published_snapshots` は DO 内にあるため公開経路が直接読むと DO を起こしてしまう。この矛盾は第12章の「publish 時に公開用 DB へ write-through、公開経路は公開用 DB のみを読む」で解消する。

この非対称は第3章のコスト制約（ハイバネーション前提・公開 read は DO 非経由）と完全に一致する。

### tanstack-db 連携メモ

- コレクションは content_types レジストリから**実行時に生成**し、typed collection として扱う。
- 関係は live query の cross-collection join で解決。多態関係は単一 join で表せず、許可型ごとに解決する（多態のコストとして受容済み）。

## 9. プラグイン（モジュール）システム

### 9.1 正体と信頼モデル

サードパーティ拡張のための汎用プラグイン機構ではなく、**ファーストパーティの機能モジュールをメタモデル上に疎結合に載せる仕組み**とする（論点O）。

- **サンドボックスなし**。信頼できないコードの分離・権限制限・リソース制御（Workers for Platforms 相当）は行わない。「自分専用の理想 CMS」が原則のため不要。
- **外部互換保証・バージョニングなし**。API 境界を第三者に対して永久保証する負担を負わない。
- モジュール境界の価値は「他人に書かせる」ことではなく、**リーンなコアの実現**にある。有効化していないモジュールのコードは走らない（当初の不満「多機能ゆえのパフォーマンス低下」への直接の解）。

### 9.2 モジュールが触れる4面

- **面1 データ拡張**: `content_types` に型を登録（`source='plugin'` / `plugin_id`）。既存機構そのまま、新規設計不要。
- **面2 サーバーロジック（フック）**: コンテンツのライフサイクルに反応。下記2種。
- **面3 管理画面 UI 拡張**: スロット方式を基本、複雑な画面のみ独自ルート（論点P）。
- **面4 外部インターフェース**: 公開エンドポイント / 外部送信 / Webhook。Queues 経路に乗る。

### 9.3 フック機構（論点N: ハイブリッド）

- **同期バリデーションフック（DO 内）**: 書き込み経路内で実行し、書き込みを**拒否できる**。single-writer なので検証と書き込みが競合なく原子的。例: `booking.beforeWrite` で空き枠検証。
- **非同期副作用フック（Cloudflare Queues）**: DO はコミット後にイベントを発火するだけで即ハイバネート。consumer Worker が外部副作用（メール送信・Webhook）を DO の外で処理。
- **確定制約**: Queues は at-least-once 配信のため、**副作用フックは冪等必須**（例: `send_log` 照会で二重送信防止）。

### 9.4 書き込み経路へのフック挿入

```
1. DO が書き込みを受ける（single-writer）
2. 有効モジュールの同期 beforeWrite フックを順に実行 → 拒否されれば中断
3. records に書き込み + relations 行を作り直す
4. コミット
5. afterWrite / afterPublish イベントを Queues に発火 → 即ハイバネート
6. consumer Worker が拾い、冪等に副作用を実行
```

ステップ2が DO 内なのは整合性（single-writer の強み）、ステップ5-6が外なのはコスト（ハイバネーション）。第3章と整合。

### 9.5 モジュール有効化（論点Q: テナントごとレジストリ）

- 各テナントの DO 内に**有効モジュールIDの config** を持つ（DO 自身がフック配送のため自分の有効モジュールを知る必要がある）。
- 無効なモジュールのフックは配送されず、コードが走らない。ブログ用途のテナントは予約を無効化＝予約コードは一切実行されない。
- ビルド時静的（全テナント同一機能セット）は、使わない機能を全テナントに積むことになり不採用。
- **適用済みマニフェスト version の記録**: この有効化レジストリに、モジュールごとの「適用済み型定義マニフェスト version」（`(module_id, applied_manifest_version)`）も同居させる。第4.2章のマイグレーション配信が冪等・バージョン管理であるための、各 DO 側の適用状態の置き場。第11.5章のモジュール権限展開表もここに同居する。

### 9.6 時限実行（論点R: DO alarm の疎な運用）

- メール予約送信・予約リマインダー等の時刻トリガーは **DO alarm** で実現。
- **重要な制約**: Durable Objects の alarm は **1オブジェクトにつき1本**。複数モジュールがそれぞれ alarm を持つことはできない。したがって **DO コアが単一 alarm を所有する多重化レイヤー**を持つ:
  - 各モジュールは「次回処理時刻」をコアの**alarm レジストリ**（DO 内の小テーブル/config: `(module_id, next_fire_at)`）に登録する。
  - コアは全登録の**最小時刻で `setAlarm`** する。
  - 起床時、コアは期限が来たモジュールへディスパッチし、処理後に次の最小時刻で**張り直す**。
- record ごとに時刻を持たない設計は維持（モジュール単位の集約で DO の起床を最小化）。

### 9.7 公開経路からの write（非対称二経路の例外）

- 予約の「公開サイトから予約作成」は、第8章の「公開経路は read only」に対する**明示的な例外**。認証済み編集者以外が DO を起こしうる唯一のケース。
- 規約: **モジュールが明示的に公開した write エンドポイントだけ**が DO に到達しうる。濫用防止（レート制限・検証）は当該エンドポイント定義時の責務。

### 9.8 当初動機での検証結果

- **予約**: `resource` / `time_slot` / `booking` を型登録。`booking` は関係フィールド＋状態スカラー（「属性を持つ関係のコンテンツ型化」の実例）。空き検証は DO 内同期フック、確認メールは Queues 非同期。→ 新機構ゼロ、既存プリミティブの合成で成立。
- **メール配信**: `campaign` / `subscriber` / `send_log` を型登録。バッチ送信は Queues（send_log で冪等）、予約送信は DO alarm、外部送信は面4の egress。

### 9.9 面3 UI の実装方針（論点P）

- スロット方式を基本とし、管理画面コアが拡張スロットの種類（ナビ項目・編集画面パネル・ツールバー等）を定義する資産を持つ。
- 複雑な画面（予約カレンダー等）のみ独自ルート `/modules/{id}/*` に逃がす。
- スロットの具体的な種類のリストは UI 実装フェーズの仕事。本仕様では「スロット方式を採る」方針の確定のみ。

## 10. 同期プロトコル

### 10.1 前提（既存決定による制約）

同期設計の大枠は既存決定でほぼ確定している。

- **同期単位 = テナントの DO**（single-writer の権威）。クライアントは楽観的に書き、DO が正本。
- **同期対象は `records` のみ**。`published_snapshots` は公開経路の別物で非対象。`relations` は派生データで非対象（DO 側で record から relations 行を作り直す）。
- **輸送は WebSocket（Hibernation API）**。プッシュ型。
- **ID クライアント生成（ULID）＋ソフト参照**。
- クライアントは tanstack-db の型付き正規化コレクションで `records` を保持。

大枠は「WebSocket 上で record 単位の変更を、DO を正本として双方向に流す」に固まる。

### 10.2 差分の粒度（問い1）

- **record 単位で転送**。CMS の record は小さく（数KB）、同時編集頻度も低いため、フィールド単位パッチの複雑さは便益に見合わない。
- 例外余地: 構造化リッチテキスト本文が肥大化して問題になった場合のみ、本文フィールドを別扱いする余地を残す。

### 10.3 競合解決（問い2・3）

single-writer の DO が競合を判定する。分散マージの難問が「DO が順に受けて判定する」に縮む。基本は**フィールド単位マージ**:

- **別フィールドの変更** → 両立（マージ）
- **同一スカラーフィールドの競合** → LWW（後勝ち。スカラーは小さく実害小）
- **同一本文フィールド（AST）の競合** → **検知して手動解決（論点S = c）**

競合検知の基盤は `records.field_versions`（第6章）。DO はフィールドごとの counter を書き込み時に進め、クライアントが添える base version と比較して競合を判定する。

**関係フィールドの扱い（精密化）**: 同期対象外なのは `relations` の**逆引きの派生インデックス**であり、関係フィールドの**前向きの値**は record の一フィールドとして同期される（`field_versions` にキーを持つ）。関係フィールドの同一フィールド競合は既定で LWW（フィールド値まるごと後勝ち）。集合的マージ（要素の add/remove を保つ）は将来オプション。いずれにせよ最も厄介な「逆引きグラフの分散マージ」は、record からのサーバー側での relations 行の作り直しで回避される（第6章）。

**CRDT は不採用**。固定管理画面・低同時編集頻度という用途に対し、CRDT のデータ肥大と実装コストは過剰。将来「同時本文編集が頻繁で手動解決が苦痛」という痛みが出た場合に限り、本文フィールドに限定した CRDT/OT をオプションとして足す。

### 10.4 本文競合の検知機構（論点S = c の含意）

新規機構は不要。競合解決の基盤である**フィールド単位 version** により、DO は「送られてきた変更のベース version が現在より古い」ことを検知できる。本文フィールドでこれを検知したら自動マージせず、クライアントに競合を返してユーザーに採用選択を促す。フィールド単位 version の自然な延長。

### 10.5 オフライン再接続

競合解決と同じ機構で吸収する。

- オフライン中の変更は「フィールド単位 version 付き変更の列」として溜まり、再接続時に DO へ送られ、10.3 のルールで順に判定される。
- ULID とソフト参照により、オフライン中に作成した新 record とその関係も、ID 衝突なく・dangling を許容して送れる。新機構不要。

## 11. 認証・認可

### 11.1 認証と認可の分離

- **認証（AuthN）**: 「誰か」を確立する（ログイン・セッション・トークン）。
- **認可（AuthZ）**: 「何をしてよいか」を判定する。構造は第2章で決定済み（membership を入口ゲートで検証、信頼境界は Worker）。

### 11.2 認証方式とコントロールプレーンの置き場（論点T）

**中央 D1 ＋ 短命 JWT のハイブリッド**。

- ユーザー・membership・セッションの正本は**中央 D1（コントロールプレーン）**。
- ログイン時に**短命 JWT（例: 15分）**を発行し、身分情報を載せる。有効な間、Worker は署名検証だけでルーティングでき、D1 を引かない（速い・安い）。
- 失効: 短命ゆえ最大15分で自然失効。加えて重大操作（権限剥奪・BAN）は**ブロックリスト照会**で即時に反映する。ブロックリストは**KV（または Worker キャッシュ）に置き、更新は稀**（失効イベント時のみ書く）。毎リクエスト D1 を引かないため「D1 を引かない」利点を損なわない。
- 認証のたびに DO/DB を無駄に起こさない（第3章のコスト思想と一致）。

### 11.3 ロールモデル（論点U）

**RBAC を基本**とする。

- デフォルトロール `owner` / `editor` / `viewer` を用意し、大半のユーザーはこれで済む。
- 権限は**「型 × 操作」の粒度**で表現（動的に増える型に対応）。
- モジュールが**独自権限を宣言できる**（例: 予約モジュールが `booking:approve`）。モジュールシステム（第9章）と同じ「宣言をデータで持つ」思想。

### 11.4 JWT に載せるもの / 載せないもの（T × U の含意）

権限セットが動的・大規模になりうる（型が増えるほど権限が増える）ため、JWT には**変わりにくく小さいものだけ**載せる。

- **載せる**: `user_id` / `tenant_id` / `role`（粗い役割名）/ 発行・失効時刻。
- **載せない**: 型 × 操作の権限マトリクス。`role` 名からサーバー側（Worker/DO）で展開する（role → 権限の展開表は中央 D1 またはモジュール定義にある）。
- JWT は「粗い身分証」に留める。細かい認可はサーバー側の権限表で行うため、型が増えても JWT は陳腐化しない。

### 11.5 認可の2段階（2場所）

型 × 操作粒度を入れた結果、認可は1箇所では終わらず、情報のある場所に応じて2段に分かれる。

- **第1段（Worker 入口・粗い）**: 「このユーザーはこのテナントのメンバーか」。JWT 署名検証 ＋ `tenant_id` 照合のみ。通らなければ DO を起こさない（コスト保護＝第3章）。
- **第2段（DO 内・細かい）**: 「*この型のこの操作* をしてよいか」。型 × 操作の権限表を見る。`content_types` とモジュール権限宣言が DO 内にあるため、ここでしか判定できない。
- 第2段は書き込み経路の `beforeWrite` フック（第9章）と**同じ場所・同じ機構**で走る。認可チェックは実質「システム定義の `beforeWrite` フック」として、モジュールのフックと同じ仕組みに乗る。
- **権限展開表を DO へ届ける経路**: 判定は DO 内で走るため、展開表が DO ローカルに要る。**デフォルトロール（owner/editor/viewer）の権限はコードに直接定義する**（アプリと共にデプロイ）。**モジュール宣言の権限は、モジュール有効化時にテナント DO の config へ書き込む**（第9.5章の有効化レジストリと同じ経路）。これで第2段判定は DO 内で完結し、外部照会を伴わない。

### 11.6 特権テナントの認証（論点V）

- **別ログイン経路**とし、可能なら多要素。権限の非対称が極端なため、通常ユーザーと同じ扉に置かない。
- 「全テナント管理」操作は通常の第2段認可を飛び越える **super 権限**。その行使は**監査ログに残す**（強い権限には記録を伴わせる）。

### 11.7 公開経路の write（論点W）

- 認証系から切り出し、「**公開エンドポイントの責務**」として濫用防止層で守る。
- 公開 write は**第1段（メンバーシップゲート）を持たない**経路。代わりに濫用防止層（レート制限・入力検証・エンドポイントごと許可リスト）を第1段の位置に置く。
- 第2段は残る: モジュールが「この公開エンドポイントは `booking:create` のみ許可」と宣言する。
- 詳細仕様は実装フェーズ送り。

## 12. 公開配信レイヤー（公開 read の物理設計）

第8章の「公開 read は DO を経由しない」と第7章の「公開が読むのは `published_snapshots`」は、`published_snapshots` が DO 内にある以上そのままでは両立しない。この章がその矛盾を解く。原則は **CQRS 的な読み取りモデルの分離**——正本（DO 内 snapshot）から、公開専用の**派生読み取りモデル**へ publish 時に write-through する。

### 12.1 正本と読み取りモデルの分離

- **正本**: `published_snapshots`（DO 内）。publish 時点の姿を保存したもの。公開経路は**ここを直接読まない**（読むと DO が起きる）。
- **公開読み取りモデル（公開用 DB）**: DO の外にある**クエリ可能な派生ストア**。公開 API はここだけを読む。DO を起こさない。

### 12.2 反映先: 公開用 DB（`PROJECTION_DB`、共有 D1）＋ `tenant_id`（プラットフォーム制約による決定）

**プラットフォーム事実**: D1 の Worker バインディングは wrangler に**静的宣言**が必要で、DO の `idFromName()` のような実行時アドレッシングが存在しない。テナントごとに D1 を動的にバインドする手段は現状なく、唯一の方法は Workers API での再デプロイ（Cloudflare 公式回答、ETA 未定）。REST API 経由はアカウント全体のレートリミットを共有するため、最もトラフィックの多い公開 read 本線には載せられない。よって **テナントごとの公開用 DB は現行プラットフォームで実装手段が事実上ない**。

したがって反映先は **`tenant_id` 列を持つ共有 D1**（静的にバインド可能）を採る。

**脅威モデルの再整理（なぜ公開用 DB は共有でよいか）**: 書き込み側で物理分離を選んだ論拠は「非公開データの秘匿性を、論理でなく物理で守る」だった。しかし**公開用 DB に入るのは publish 済み＝公開を意図したデータのみ**であり、守るべき秘匿性が原理的に薄い。分離の論拠は公開用 DB には外挿できない。行レベル分離の残余リスク（クエリの絞り込みミス）で漏れるのは「いずれ公開される/された情報」であり、実害が桁違いに小さい。ゆえに公開用 DB 側だけ「コンテンツ系に `tenant_id` を持たない」原則（第2・6章）を破ることは、**「公開用 DB は正本ではない使い捨ての派生物」**という位置づけで整合的に説明できる。

**成長路線**: 単一共有 D1 は 1DB 10GB 上限とクエリ集中がいずれ問題になる。規模が育ったら**固定 N 本のシャード D1**（静的バインド可能な本数）に tenant をハッシュ配置する。共有案の自然な発展形で、10GB 上限とロード分散の双方の解決になる。per-tenant の完全分離が本当に要るなら Workers for Platforms での User Worker 個別バインドは可能だが、9.1 で WfP 相当を不採用としており公開用 DB のためだけの導入は過剰。

**公開用 DB の物理設計（3テーブル＋カタログ）**: 共有 D1 では全テナント・全型が一枚の `projected_records` を共有するため、**テナントごとに DB を持つ時代の「宣言フィールドを実カラムへ切り出す」戦略は成立しない**（(テナント × 型) ごとに異なる切り出しカラムが一枚に載らず、カラムが際限なく増え名前も衝突する）。代わりに2段構えで索引を機能させる。

- **`projected_records`**: `(tenant_id, record_id, type, slug, published_at, data, source_version)`。**システム共通フィールドのみ実カラム**（どのテナントでも意味が同じもの）。複合索引 `(tenant_id, type, published_at)`・`(tenant_id, type, slug)` を張り、**一覧クエリの大半（最新N件・slug 単体取得）はこれで完結**。型固有フィールドは `data` JSON に残す（実カラムに切り出さない）。
- **`projected_relations`**: `(tenant_id, source_id, source_field, target_type, target_id, ordinal)`、**published なもののみ**。`(tenant_id, target_id, source_type)` 等に索引を張り、メンバーシップフィルタ（「カテゴリXの記事」）と逆引きを O(log n) で解く。
- **projection_index（索引専用サイドテーブル）**: ユーザー宣言の `indexed` フィールドはここへ。`(tenant_id, type, field_key, value_text, value_num, value_date, record_id)` で `(tenant_id, type, field_key, value_*)` に索引。フィルタ/ソートでここが `record_id` を絞り、実体は `projected_records` の `data` へ**1回 join** で取る。
- **projection_fields（フィールドカタログ。Phase 5b で追加）**: `(tenant_id, type, field_key, kind, multi)`。公開 read API が「フィルタ/ソート可能なフィールドか・値がどの型別カラムにあるか・複数値か」を **DO を起こさずに**知るための、content_types の索引宣言部分を公開用 DB に反映したもの。「フィールドの型は `content_types` から既知なので、クエリ層が適切な列を選べる」（上記）の公開側の実体がこの表になる。record の upsert と同時に LWW で更新し、公開用 DB の再構築の mark-and-sweep が宣言から消えた行を削除する。

> **EAV との区別（第6章の却下理由と混同しないための一文）**: projection_index は形の上では EAV だが、第6章が EAV を退けた理由（「1レコード復元に自己 join の山」）は**当てはまらない**。この表は**レコードを復元するためではなく、フィルタ/ソートで `record_id` を絞るためだけ**に使い、実体は `projected_records` から1回の join で取る。`projected_relations` が「メンバーシップフィルタ専用の索引」であるのと同じ役割分担で、既にある公開用 DB の思想と揃う。**復元用 EAV は却下・索引用サイドテーブルは可**。

- **値の型付き格納（正しいソート/範囲のため）**: projection_index の値は型別カラム（`value_text` / `value_num` / `value_date`）に振り分ける。数値・日付を TEXT 一列で持つとソート/範囲比較が壊れる（数値の文字列ソート問題）。フィールドの型は `content_types` から既知なので、クエリ層が適切な列を選べる。
- **複数 indexed フィールドの同時フィルタ**は索引2引きの交差になるが、公開一覧の複雑度として許容範囲。12.4 の「フィルタ/ソートは索引宣言済みフィールドに限る」という指定できる値の制限が、ここでも複雑度の上限として機能する。

**ランタイム DDL の受容（範囲が縮小）**: 共有 D1 化により、宣言フィールドは実カラムでなく projection_index の行になったため、**型定義のたびに公開用 DB へ DDL を打つ必要はほぼ消えた**（`projected_records`・`projected_relations`・projection_index・projection_fields の4スキーマは固定）。残る DDL はシステム共通カラムの変更程度で稀。いずれにせよ公開用 DB は snapshot から再構築可能な派生物であり、版数分裂は公開用 DB の再構築で解消できる（第6章の table-per-type 却下と衝突しない理由は同じ）。

### 12.3 公開用 DB の更新: アウトボックス ＋ 非同期冪等反映

**dual-write 問題**: DO-SQLite のコミットと公開用 DB への書き込みは**別システムへの2書き込みで、分散トランザクションがない**。同期 write-through にすると D1 側失敗（障害・レート制限）で正本と公開用 DB が乖離し、「snapshot はあるのに公開されない・編集者には成功に見える」という故障モードを生む。したがって同期 write-through は採らず、**アウトボックスパターンで Queues に載せる**。

- **publish/unpublish 処理**: DO-SQLite 内で snapshot 作成/削除 ＋「反映ジョブ」をアウトボックスとして記録し**コミット**（ここまで単一 DB 内で原子的）。
- **公開用 DB の upsert/delete**: Queues 経由の consumer が**冪等に**実行（第9.3章「副作用フックは冪等必須」と同じ規約に乗る）。
- **順序逆転への防御（upsert）**: 公開用 DB の行に `source_version` を持たせ、「**現在の公開用 DB の行より古い version の upsert は無視する**」ガードを入れる（publish 直後の unpublish が先に着く等に耐える）。
- **順序逆転への防御（delete）**: delete ジョブにも**発行時点の version を載せ**、「**公開用 DB の行の `source_version` がそれより新しければ delete を無視**」する。unpublish 発行後に republish が先着し、遅れて届いた delete が消してしまう事故を防ぐ。
- **アウトボックスの送出保証（sweeper・クラッシュ耐性）**: 拾い直しを **sweeper** が担い、**9.6 の alarm 多重化レジストリにシステムモジュールとして登録**する。ただし「enqueue 失敗を観測したら登録」では、コミット直後・enqueue 前に DO が落ちた場合（evict・デプロイ・例外）に登録者が不在となり publish が宙吊りになる（低トラフィックなテナントほど長引く）。したがって保証を「失敗の観測」ではなく「**コミットの事実**」に依存させる: **outbox 行を書くのと同一コミットで sweeper の `next_fire_at`（数秒後）を alarm レジストリに登録**する。両者は同じ DO-SQLite 内なので単一トランザクションで原子化できる。sweeper は起床時に未送出行を再送し、**全行送出済みなら no-op で登録を消す**（冪等ゆえ正常系で毎回登録しても実害なし）。
- **反映 consumer の3テーブル更新の原子性**: republish の upsert は `projected_records` の行更新に加え、その record の `projected_relations`・projection_index の**旧行削除→再挿入**（DO 内の relations 行の作り直しと同じパターン）を伴う。version ガードの判定（record 単位で一度）と3テーブルの置き換えは D1 の `batch()`（暗黙トランザクション）で一括実行し、半端な状態を残さない。
- 代償は「publish が公開用 DB に反映されるまで数秒の結果整合」。公開配信では完全に許容範囲。

編集（draft 同期）は公開用 DB を触らない。第7章「publish がキャッシュ無効化の唯一トリガー」とも整合（無効化もこの consumer が担える）。

> **アウトボックステーブル**（DO 内）: `outbox (id, job_type, record_id, source_version, enqueued_at, sent)`。`job_type` は upsert/delete、`sent` は送出済みフラグ。スキーマは第6章の運用テーブル群に置く。**掃除**: `sent=1` の行は単調増加するため、送出確認後に削除、または一定期間後に purge する（デバッグ用に短期保持は可、方針だけ固定）。

### 12.3b 公開用 DB は再構築可能な派生物（再構築ジョブ）

**原則**: 公開用 DB はいつでも DO 内 snapshot から**決定的に再構築できる使い捨ての派生物**である。これは `relations` が record から relations 行の作り直しで復元可能な派生データ（第6章）であることの完全な相似形で、設計思想の統一になる。

テナント単位の**公開用 DB の再構築ジョブ（Queues 経由・冪等）**を第一級の機構として持つ。用途:

- dual-write 乖離の最終防衛線（乖離検知時に snapshot から作り直す）。
- **`indexed` の後付け変更のバックフィル**: 新たに `indexed` 宣言したフィールドは、既存の公開済み record について projection_index の行が無い。公開用 DB の再構築が `projected_records` の `data` から値を抽出して projection_index を埋め直す（DO 側の VIRTUAL generated column は既存行を書き換えないが、公開用 DB 側のサイドテーブルはバックフィルが要る、という非対称）。
- 型定義変更・公開用 DB のスキーマ変更・障害復旧・（将来）シャード再配置。

> **共有 D1 への書き込み集中（運用注記）**: 通常の publish 頻度では問題にならないが、**テナント全体の公開用 DB の再構築ジョブ**は共有 D1 の書き込みプライマリに負荷が集中しうる唯一の経路。再構築は**バッチ化し、consumer の並列度を絞る**こと。

### 12.4 公開 API のクエリで指定できる値

公開用 DB に対して、公開 API は最小限のクエリを提供する:

- **単体取得**: id または slug で1件。
- **一覧取得**: 型指定 + フィルタ（**索引宣言済みフィールド**の等値・関係メンバーシップ）+ ソート（索引宣言済みフィールド、例 `published_at` 降順）+ ページネーション（カーソル/limit）。
- フィルタ/ソートは**索引宣言済みフィールドに限る**（無制限クエリは許さない＝公開用 DB のカラム設計と一致）。
- **複数値フィールドの意味論**: enum（複数選択）を indexed 宣言すると projection_index は「1値=1行」で複数行になり、フィルタは自然に any-of 意味論になる（row-per-value の利点としてそのまま受容）。ただし**ソート可能なのは単一値の索引フィールドのみ**（複数値フィールドのソートは未定義）。

### 12.5 公開経路での関係解決

- 公開経路の関係解決は**公開用 DB（published のみ）に対してのみ**行う。参照先が未 publish / unpublish 済みなら、その参照は**不在として扱う**（ソフト参照の公開版）。
- `snapshotEmbed=value` の埋め込み値は公開用 DB の行にインラインで載る（解決不要）。`snapshotEmbed=id` は公開用 DB 内で解決し、解決先が非公開なら不在。
- **編集 UX**: 未公開の参照先を持つ record を publish しようとしたら**警告**する（公開すると当該リンクが不在になる旨）。ソフト参照方針によりブロックはしない。

### 12.6 キャッシュ戦略

- 一覧・単体の**正確性は公開用 DB の更新で担保**される（publish から数秒の結果整合。コールドキャッシュ時は公開用 DB を読む＝DO 非経由、404 にならない）。
- エッジキャッシュ（Cache API / KV）は公開用 DB の**前段の遅延最適化**。無効化は publish/unpublish 時にキー単位パージ、または短 TTL で陳腐化を有界化。一覧の厳密なタグ無効化に依存しなくても、公開用 DB 側の値は正しいので、キャッシュの古さの実害は小さい。

### 12.7 コスト整合

- 公開 read は公開用 DB（スケール・トゥ・ゼロ、レプリカ）とエッジキャッシュのみを叩き、**DO を起こさない**——第3章のハイバネーション前提を維持。
- 唯一の例外は第9.7章の公開 write（DO 到達）で、これは第3章のコスト攻撃面注記のとおり Worker 層で DO 到達前に防御する。

## 13. 非目標（Non-Goals）

以下は CMS として必ず問われるが、**現時点では意図的にやらない**。「考慮した上での非目標」であり「見落とし」ではない。各項目に、目標化する際に**再訪すべき既存決定**を添える（将来の格上げ時の地図として）。

- **全文検索（公開側）**: 公開用 DB に対する全文検索は現状スコープ外。筋道は明確で、**公開用 DB（第12章）に SQLite FTS5 で全文索引を足す**のが既存構造に最も素直に乗る（公開検索の置き場＝公開用 DB）。目標化時に第12章の公開用 DB のテーブル設計に FTS を追加する。**編集側（下書きを含む）の全文検索は第16章で目標化した**（DO-SQLite の FTS5。エージェントの `record_search` が必要とするため。決定 43）。意味検索は方式未定で引き続き非目標。
- **i18n / 多言語**: スコープ外。**最も緊張が強い**——alt/caption を**アセット内在**にした決定（第5章・論点E）は多言語と構造的に衝突する（多言語では alt は「アセット固有」でなく「アセット×言語」になる）。目標化するなら、alt 内在の判断と、より広く「コンテンツの言語軸をどうモデル化するか（型ごとロケール別 record か、フィールド内ロケールマップか）」を再訪する必要がある。第5回で「文脈依存 alt は入れ子禁止(B)と衝突するため内在にする」とした判断が、ここで再浮上する。
- **アセット変換パイプライン**: スコープ外。R2 にバイナリを置く（論点E）までは決定済みだが、画像リサイズ・variants 生成は未定義。**Cloudflare Images に逃がす**か Workers で変換するかは、公開 read パス（DO 非経由・第12章）との相性を見て決める。目標化時は配信経路への影響を要検討。
- **バックアップ / テナントのエクスポート**: スコープ外。DO-SQLite の PITR（Time Travel）は「時間を巻き戻す」であって「テナント単位の**可搬な形式で吐き出す**」とは別問題。メタモデルゆえ、エクスポートは「型定義（content_types）＋records＋relations＋アセット」を一括で可搬にする**形式設計**が要る。正本が DO 内にあるため、DO からのダンプ経路も設計対象。
- **DO のロケーション（地理分散編集）**: **前提として明記**。DO は単一リージョンに固定されるため、編集者が地理的に分散すると同期レイテンシに直撃する。本設計が「自分専用の理想 CMS」（第14決定＝原文の設計前提）である限り**非問題**。将来テナントを他者に開き、かつ編集者が広域分散する運用を目標化するなら、この前提が崩れ、DO ロケーション戦略（location hint、リージョン選択、あるいは編集側の再設計）が必要になる。

## 16. エージェント接続（MCP）

AI エージェントが管理画面と同じ操作（record の作成・編集・公開など）を行えるようにするため、[Model Context Protocol](https://modelcontextprotocol.io/)（MCP）のサーバーを api Worker に置く。本章は MCP 導入調査レポート（第 3.1 版、2026-11-01）の論点 A〜E と、実装計画（M0〜M5）のレビューで確定した事項を固定する。試作（M0-2・M0-3）で決める事項は本章では「M0-x で決める」と明記し、結果は決定ログに追記する。

準拠する MCP 仕様は **2026-07-28 改訂**。この改訂でセッション（`Mcp-Session-Id`・`initialize`・GET エンドポイント）が廃止され、Streamable HTTP の **stateless 運用が必須**になった。`server/discover` の実装、毎リクエストの `Mcp-Method` / `Mcp-Name` ヘッダ、`tools/list` の `ttlMs` / `cacheScope`、スコープ不足の `403 + insufficient_scope`、サーバー発の問い合わせの MRTR（Multi Round-Trip Requests）化、Client ID Metadata Documents（CIMD）への移行が、本章の前提になる。

### 16.1 位置づけ: 第三の経路、既存経路の再利用

MCP は、管理画面の同期（第 8・10 章）と REST（`/v1/t/:tenantId/...`）に並ぶ **第三の書き込み経路**である。経路が増えても DO 内の処理は増やさない:

- 書き込みは `writeRecord`、公開は `publishRecord` / `unpublishRecord`、削除は既存の削除経路を通す。validate-on-write（第 4.2 章）・beforeWrite フック（第 9.4 章）・relations 行の作り直し（第 6 章）・公開用 DB への反映（第 12.3 章）は MCP 専用に作り直さない。
- MCP のツールは **操作カタログ**（16.4）の上に作る。管理画面・REST・MCP は同じカタログの操作を、経路（`via`）だけ違えて呼ぶ。
- 読み取りツール（`record_list` / `record_get`）は下書きを含むため **DO を起こす**。公開 read 経路（DO 非経由、第 12 章）とは別物であり、第 3 章のコスト制約の下で Rate Limiting（16.2）を必須にする。

### 16.2 テナント別 URL・配置・入口（論点 D1・D2・E4）

- **テナント別 URL**: `/mcp/t/:tenantId`。Protected Resource Metadata（RFC 9728）もパス付きで出し、`resource` はパス込みの canonical URI としてテナントを運ぶ。トークンは `resource` に束縛されるので、同意画面で選ぶのはスコープだけになる。
- **配置（論点 D2）**: **api Worker の直接オリジン**で受ける（`https://<api>/mcp/t/:tenantId`、決定 48）。`resource` と PRM はこのオリジンで出す。admin オリジン経由（同一オリジン転送）にはしない: MCP はセッション cookie を使わず、1 ホップ増えるだけで得るものがない。dev で api → admin の逆向き Service Binding は組める（M0-3 で確認）が、認可サーバーを api に置くので不要（16.3）。
- **認可サーバーの入口**は admin オリジンのテナント別パス `https://<admin>/oauth/t/:tenantId/{authorize,oauth/token,oauth/register}` と `https://<admin>/.well-known/oauth-authorization-server/oauth/t/:tenantId`。admin は既存の同一オリジン転送（`/auth` `/v1` と同じ仕組み）に `/oauth` と `/.well-known/oauth-authorization-server` を足して api へ渡す。ログイン状態（セッション cookie）を見るのは `/authorize` だけで、cookie は admin オリジンのものがそのまま届く。
- **トランスポート**: stateless Streamable HTTP。POST のみ受け、旧クライアントの GET / DELETE には 405、`Mcp-Session-Id` は無視する。`server/discover` を実装する。
- **ヘッダと本文の一致検証（論点 E4）**: 入口で `Mcp-Method` / `Mcp-Name` を本文と照合し、不一致は `400` + JSON-RPC `-32020` で拒否する。照合後はヘッダの `Mcp-Name`（ツール名）単位で Rate Limiting を掛ける（公開 write の `ratelimit` binding と同じ仕組み。MCP 用の namespace を別に持つ）。
- **Origin の検証**: ブラウザからの直接呼び出しを想定しないため、`Origin` ヘッダ付きの要求は許可リストに無ければ拒否する。
- セッション cookie では通さない（Bearer トークン専用。CSRF を考えずに済む）。

### 16.3 認証・認可（論点 C1〜C3）

認証と認可の構造は第 11 章を変えない。MCP で足すのは **外部クライアント向けのトークン発行経路**と、トークンに付く **スコープ**である。

**トークンの入手経路は 2 つで、どちらも恒久的な正式経路**とする:

| 経路 | 用途 | 備考 |
| --- | --- | --- |
| PAT（Personal Access Token） | Claude Code・Cursor・自作エージェント・CI など、ヘッダにトークンを貼れるクライアント。自動化・長期利用 | 管理画面で発行。D1 にハッシュ・スコープ・有効期限を保存する。有効期限に上限を設け、書き込みスコープ付きは短くする（OAuth の refresh が無いぶん、漏えいの影響を期限で押さえる）。発行できるのはテナントの所有者だけ |
| OAuth 2.1（認可コード + PKCE） | claude.ai や ChatGPT のコネクタのように PAT を貼れないホスト型クライアント | 登録は CIMD を優先し、DCR（RFC 7591、Deprecated）は fallback として残す。認可サーバーは **`@cloudflare/workers-oauth-provider` v1 の分割 API（`OAuthAuthorizationServer` / `OAuthResourceServer`）を api Worker に置く**（決定 47、M0-3 の試作 `docs/superpowers/plans/2026-11-01-m0-3-oauth-spike-result.md`）。issuer は admin オリジンのテナント別パス（16.2）、`resources` は `https://<api>/mcp/t/:tenantId` の 1 つ。どちらも URL から決まるので、認可サーバーのオブジェクトは要求ごとに組み立てる（構築コストは無視できる）。状態は api の `OAUTH_KV` に置く。access token の TTL は既存 JWT と同じ 15 分、refresh token はライブラリ既定の 30 日。同意画面は api が HTML を描画する（M3-2。admin は転送するだけで、未ログインなら admin の `/login?return_to=…` に回してから同じ URL へ戻す。`return_to` は `/oauth/t/` 配下のパスだけ許す） |

**検証と失効**: どちらの経路でも、Worker の入口でトークンを検証した後に既存の BLOCKLIST（`blocked:user` / `blocked:membership`）を照会し、同じ認可コンテキストに合流させる。BAN とメンバー削除は既に BLOCKLIST に書かれているので新規作業はない。ロール変更は BLOCKLIST に書かず、JWT と同じく TTL 内の遅れを受け入れる（`membership` キーは管理画面のセッションも止めるため）。

**検証経路の具体（決定 49）**: MCP の入口は `OAuthResourceServer` をホストにし（401 の challenge・PRM・403 `insufficient_scope` をライブラリが出す）、その `validateToken` に次の合流関数を差す。
- **PAT**: 接頭辞 `plyrs_pat_` で振り分け、D1 の `personal_access_tokens`（SHA-256 ハッシュ・テナント・スコープ・有効期限・失効日時）を `memberships` と join した 1 回の照会で検証する。ロールは PAT に焼き込まず毎回 `memberships` から引く（長命なので、ロール変更を即時に反映する）。
- **OAuth**: 同じ api Worker 内で `OAuthAuthorizationServer.validateToken`（KV 1 回 + props の復号）を呼ぶ。Service Binding の RPC は無い。ロールは同意時に grant の props に入れ、refresh のたびに `memberships` から読み直す（access token の 15 分は JWT と同じ遅れ）。
- 両方とも BLOCKLIST の 2 キーを照会し、認可コンテキスト `{userId, role, tenantId, exp, scopes, tokenId, tokenKind}` に合流する。`tokenKind`（`"pat" | "oauth"`）はトークンの種別で、書き込み経路の `via`（16.4・16.5。MCP 経由ならどちらの種別でも `via` は MCP）とは別に持つ。PAT の `tokenId` は D1 の行 ID、OAuth は grant の識別子（失効の単位に合わせる）。

**スコープ（論点 C3）**: DO の `Operation`（`record:read` `record:write` `record:delete` `record:publish` `type:manage` など、`auth/permissions.ts`）をそのままスコープ名にする。**実効権限 = スコープ ∩ ロール**を DO の第 2 段（第 11.5 章）で判定する。スコープは権限を絞るだけで増やさない。認可コンテキスト `{userId, role, tenantId, exp}` に `scopes` と `tokenId` を足し、`record:read` の `requireOperation` を MCP で初めて実装する（読み取り拒否はここが最初）。型単位のスコープ（例 `record:write:article`）は初期には採らない（第 11.4 章の決定の見直しが先。未処理論点）。

**同意画面とセッション cookie**: 管理画面のセッション cookie は `SameSite=Strict`（CSRF の前提）のまま変えない。ホスト型クライアントから `/authorize` へ遷移すると cookie が送られないので、ログイン済みでも毎回 `/login` を経由して同じ URL へ戻る（仕様。M4-0b で確認）。同意 POST は保存済み要求の `resource` が URL のテナントのものかを照合し、`/authorize` の GET はセッションを確かめてから要求を解釈する（CIMD の外向き fetch を未ログインの要求で起こさない）。会員解除・BAN では PAT と同じく OAuth の付与も失効させる。

**publish 権限の既定（論点 C5）**: PAT の発行画面と OAuth の同意画面の両方で、`record:publish` は **既定で外し、所有者だけが付与できる**。既定は人が公開する。

### 16.4 操作カタログ（論点 B1）

「操作名・入出力の Zod・必要な `Operation`・`readOnlyHint` / `destructiveHint` / `idempotentHint`・説明文・提供する経路（`via`）」を **1 か所で宣言**し、MCP のツール、REST、将来の CLI をここから生成する。

- 実行は DO への RPC 1 本 `invoke(op, input)` に集約する。RPC を操作ごとに増やすと `rpc-unwrap.ts` が対処している union の潰れが操作ごとに再発するため。
- JSON Schema は zod 4 の `z.toJSONSchema` で生成する。`tools/list` は決定的な順序で返し、`ttlMs` / `cacheScope` を付ける。
- 経路の列挙（管理画面の同期 / MCP / REST）は、変更履歴の `via`（16.5）と判定モードの選択（16.6）で共通に使う。別々に作らない。
- 既存の REST `PUT /records/...` は `baseFieldVersions` を持たない無条件上書きで同期経路と挙動が違う。カタログ化の際に `baseFieldVersions` を必須にし、同期と同じ競合判定に通す（破壊的変更だが利用者はいない）。
- モジュール（第 9 章）は manifest に MCP ツールを宣言でき、カタログに取り込まれる（M5）。モジュールのフックは `writeRecord` 経由で自動的に適用される。

### 16.5 変更履歴（論点 A2・C4）

record の変更履歴を **DO 内**に置く。履歴表のキーは **履歴表自身の連番**（record ごとに単調増加）とし、`records.version` は属性として併記する。`records.version` は `writeRecord` でしか増えず publish / unpublish では変わらない（第 7 章、`do/publish.ts`）ため、publish で切った版を直前の編集版と区別するには独自のキーが要る。publish の版には `published_snapshots.source_version` と同じ値を持たせ、公開版を履歴の 1 点として参照できる形にし、`compare`（公開版との差分）と `history` を同じ表から作る。`audit_logs` は super / tenant / member / dlq 系の操作だけを記録するため、record 編集の記録の置き場はこの履歴になる。

- **区切り規則**: 書き込みごとに版を作らない（同期の push は入力中の細かな差分で届く）。次のいずれかで新しい版を切る: (1) actor（誰の権限か）または `via` が前の版と違う、(2) 前の版から **15 分**以上経っている、(3) `status` が変わる、(4) publish / unpublish。それ以外の連続した書き込みは直前の版に畳み込む。
- **記録する属性**: 履歴の連番、`records.version`、publish の版なら `source_version`、`data` と `fieldVersions`、`status`、actor（`userId`）、`via`（管理画面の同期 / MCP / REST）、MCP と OAuth では `tokenId` と `client_id`。`clientInfo` は自己申告で未検証なので表示の補足に限り、認可には使わない。
- **保持（仮置き。M4-6 で実測して見直す）**: 1 record あたり **最新 100 版**かつ **365 日**。直近 10 版は全文、それより古い版は **1 つ新しい版からの逆差分**（`{set, unset}`）で保存する。逆差分にするのは、復元を新しい側（常に全文がある）から辿るためで、保持上限で古い版を消しても残った版の鎖が切れない。publish / unpublish の区切りの版は **常に全文**で持ち、保持上限に達しても **record が存在する間は消さない**（公開版の履歴を失わないため。差分の鎖の途中に残っても全文なので復元の起点になる）。
- **実装の置き場（M2-3a）**: `packages/db/src/schema.ts` の `record_history`（主キー `(record_id, history_seq)`、`changed_fields` に直前の版との差分キーを持つ）と `apps/api/src/do/history.ts`。`writeRecordCore` が INSERT / UPDATE の直後に `recordHistory()` を呼び、`applied: false` の書き込みは記録しない。区切り規則の (2) は「前の版を**開いた**時刻（`created_at`）から 15 分」で、畳み込みで `updated_at` が進んでも起点は動かない。経路の列挙 `Via`（`"sync" | "mcp" | "rest"`）は `@plyrs/sync-protocol` が正本で、モジュールの書き戻し・alarm・アップロードなど同期でも MCP でもない書き込みは `rest` に分類する。
- deleted_at の付いた record の履歴も残し、削除の取り消し（`record_restore`）に使う。publish と delete は `writeRecord` を通らないので、それぞれに記録点を足す。
- `restore` は `writeRecord` を通す。validate-on-write の対象なので、型定義が変わっていれば失敗しうる（遅延マイグレーションの帰結として受け入れる）。
- 履歴と FTS5（16.9）は DO-SQLite の容量と書き込み行数を増やす。区切り規則と保持上限で有界化し、M4 で実測する。

### 16.6 競合判定とエージェント経路（論点 B3）

新しい `_rev` は作らない。`record_get` が返す既存の `fieldVersions` を、更新時に `baseFieldVersions` として **必須**にし、`resolveSyncWrite`（第 10.3 章）に通す。

- **判定モード**: `resolveSyncWrite` に判定モードの引数を足す。管理画面の同期は現行どおり（別フィールドはマージ、同一スカラーは LWW、同一リッチテキストは conflict）。**エージェント経路の既定は strict**（`changedFields` のどれか 1 つでも version が違えば、スカラーも含めて conflict）。エージェントが人の直前のタイトルや slug の編集を黙って上書きするのを避けるため。ワークフロー状態（`status`）には fieldVersion が無いので、`status` を変える更新は `baseFieldVersions` が現在の `fieldVersions` 全体と一致することを要求する（人が進めた状態を、古い record を見たエージェントが黙って戻さない。M2 レビューで追加）。
- **競合応答**: `isError: true` で、現在値・現在の `fieldVersions`・競合フィールドを返す。`record_update` の `outputSchema` は成功形と競合形の oneOf にする（`structuredContent` は `outputSchema` に準拠しなければならない）。
- **再適用の打ち切り**: ツール説明で再適用を 2 回までとし、超えたら提案（16.8）へ回すよう競合応答で導く。stateless なのでサーバーは回数を知らない。回数は `record_update` の `attempt` 引数で自己申告させる（改ざんできるが用途が導線なので足りる）。
- **ブロック単位の競合判定**は、リッチテキストのブロック ID（16.10）が確定した後に、`fieldVersions` をブロック単位にするか DO 内 3-way merge にするかを決める（M5。未処理論点）。

### 16.7 冪等性とエラーの層分け（論点 E2・E3）

**冪等性（E3）**: 応答ストリームが切れたらクライアントは新しい request ID で再発行する（仕様の MUST）ため、書き込み系ツールは冪等でなければならない。

- `record_create` はクライアント指定の UUIDv7 を受ける（第 6 章の DDL は ULID と書くが、tech-selection 2.10 で UUIDv7 に読み替えている。その規約と同じ）。同じ ID で同じ内容なら既存の結果を返し、内容が違えば `already_exists` で拒否する（切断後の再送と、ID の使い回しという誤用を区別する）。
- `publish` / `unpublish` / `delete` は状態遷移として冪等にする（既にその状態なら成功を返す）。

**エラーの層分け（E2）**: 3 層に分け、クライアントが「再認可すれば通る」か「内容を直す」か「実装が違う」かを区別できるようにする。

| 層 | 例 | 返し方 |
| --- | --- | --- |
| トークンのスコープ不足 | `record:publish` の無い PAT で publish | HTTP `403` + `WWW-Authenticate: Bearer error="insufficient_scope", scope="…"`。必要なスコープは 1 回の challenge にまとめる。OAuth 接続は step-up（再認可）し、PAT 接続は `error_description` の導線（所有者が該当スコープ付きの PAT を発行する）に従う |
| 業務エラー | ロール不足・検証失敗・一意性違反・競合・`already_exists` | `isError: true`。ロール不足は DO の第 2 段で判定し、再認可しても変わらないのでこちら。`structuredContent` に `code` / `details` を載せ、業務エラーの形も `outputSchema` に含める |
| プロトコル違反 | ヘッダと本文の不一致、不正な JSON-RPC | JSON-RPC エラー。仕様が定めるコード（`-32020〜-32099` は MCP 予約。例: ヘッダ不一致の `-32020`、16.2）はそのまま使う。独自コードは `-32000〜-32019`（implementation-defined）か予約範囲 `-32768〜-32000` の外に置く |

### 16.8 publish の方針と確認（論点 C5・B4）

**既定は人が公開する**。エージェントには `status` を `in_review` / `ready` まで進めさせ、公開は人が管理画面で行う運用を基本にする（第 7 章の「公開軸とワークフロー軸の直交」が、この分担を自然に表す）。

- `record:publish` は既定の付与から外す（16.3）。所有者が付与した場合に限り、エージェントが publish ツールを呼べる。
- **publish ツールの出し方**: `tools/list` は接続ごとに変えてはならないが、要求に示された認可で変わるのは許される。付与スコープで出し分ける（`cacheScope: "private"`）か、常に出して `403 + insufficient_scope` で step-up させるかは M4-2 で決める。仮置きは後者（publish 権限を後から付与する運用に合う）。
- **確認は 2 系統**: ① 同じ利用者への確認は MRTR の elicitation で行う（クライアントが能力を宣言していなければ送れない。`requestState` は攻撃者が操作できる入力として扱い、HMAC / AEAD で保護し、principal・TTL・元要求のダイジェストを照合する）。② 別の人（所有者）の承認と、elicitation に対応しないクライアントは **提案（change set）**へ回す。提案ができるまでは拒否して人に回す。
- **提案（change set、論点 B4）**: 直接書き込みに加え、変更を「提案」として保存し、管理画面で差分を見て採用・却下する経路を M5 で置く。`record:propose` だけを持つトークンの変更は提案になる。公開状態・ワークフロー状態（第 7 章）に加える 3 本目の軸であり、再適用の打ち切り先（16.6）の受け皿にもなる。

### 16.9 一覧と検索（論点 A4）

- **一覧（`record_list`）は初期リリースに必須**。文法は公開 API（第 12.4 章、`filter[...]` / `sort` / `include` / `cursor`）に揃え、文法の解釈は `public/query.ts` を共有する。実行器は `records.data`（JSON）に対して新しく作る（公開側の出力型は公開用 DB の索引列に結び付いているため）。
- フィルタできるフィールドは公開側と同じく **索引宣言済み + システム列**（`type` / `status` / `updated_at`）に限る（仮置き。無制限に `json_extract` を許すと DO の行読み取りが膨らむ）。`limit` に上限を設ける。`cursor` は同期の `seq`。下書きを含め、削除済みは除く。
- **下書きを含む全文検索**（`record_search`、M2-9 で実装）は DO-SQLite の **FTS5** 仮想テーブル `records_fts` で作り、`writeRecord`（索引の張り直し）と削除（索引から外す）で更新する。対象は text フィールドの値と richtext のプレーンテキスト（json / relation / 数値 / 日時 / select は含めない）。tokenizer は **trigram**（日本語の分かち書きが不要）で、3 文字以上の語は `MATCH`（語ごとに引用符で囲み AND）、**2 文字以下の語を含む問い合わせは `LIKE` の部分一致**に落とす（trigram は 3 文字未満に一致しないため）。既存 record を索引に入れるため、DO 起動時の一回限りの再索引（`do_config.search_indexed`）と、公開用 DB の再構築と同じ形の super の再索引（`POST /super/v1/tenants/:tenantId/search-reindex`）を持つ。FTS5 への書き込みも rows written に計上される。FTS5 は全文索引を持つ列にしか索引を持たないため、索引行の `rowid` を `records.rowid` に揃え、張り直し・削除は `rowid`（FTS5 の主キー）で引く（UNINDEXED 列で引くと内容表の全走査になり、書き込み 1 回の rows read がテナントの record 数に比例する。第 3 章のコスト構造に反する）。FTS5 の仮想テーブルは drizzle のスキーマで表せないため、このマイグレーションだけ `drizzle-kit generate --custom` で作って手で書く。
- これは第 13 章の非目標「全文検索」からの部分的な格上げである。**公開側（公開用 DB）の全文検索は引き続き非目標**。意味検索は方式未定（M5）。

### 16.10 リッチテキスト（論点 A1・E1）

**決定事項は「最上位ブロックへの安定 ID 付与」**であり、形式の変更ではない。部分編集・ブロック単位の競合判定・生成しやすさは、いずれも安定 ID から来る利点で、特定の形式に固有ではない。

- **形式は (a) ProseMirror JSON のまま各最上位ブロックに `attrs.id` を持たせる（`@tiptap/extension-unique-id`）**。M0-2 の試作（`docs/superpowers/plans/2026-11-01-m0-2-richtext-spike-result.md`）で、Tiptap の全ノード種 19 件の往復が (a) と Markdown では全て可逆、(b) Portable Text では入れ子ブロックが無いため 5 件が不可逆（番号リストの start、項目内の複数段落、引用内の複数段落・リスト、空白）と出たため。(b) は影響する PR も 4〜5 本の L に膨らむ。論点 A（JSON AST 採用、tech-selection 2.7）は維持する（決定 46）。
- `RICH_TEXT_SCHEMA_VERSION` を 2 に上げ、v1 のエンベロープを読むときに最上位ブロックへ ID を振り、次の書き込みで永続化する（一括変換しない。第 4.2 章の遅延マイグレーション）。**読むときの ID はランダムにせず、ブロックの位置と内容のハッシュから決定的に導く**。未更新の record でも `record_get` で見た ID が `record_update` で通り、その間に内容が変われば `baseFieldVersions` の不一致で競合になる。永続化後は保存された ID を優先する。
- **Markdown ⇄ AST の双方向変換**は `@tiptap/markdown` の `MarkdownManager` を Editor 無し・DOM 無しで Worker に置く（試作で動作を確認）。変換後は必ず ProseMirror のスキーマ検証を通し、語彙に無い構造（表・タスクリスト・外部 URL の画像など）は業務エラーで返す。エージェントは Markdown で読み書きし、複雑なブロックだけ AST を直接送る。独自ノードの Markdown 文法（M2-2 で確定）: record 参照は Tiptap の inline shortcode `[@ recordType="author" recordId="<uuid>" label="山田"]`、本文中画像は標準の画像構文で href を独自スキームにした `![label](plyrs://asset/<uuid>)`。外部 URL の画像・表・タスクリストは語彙に無いので `unsupported_markdown` の業務エラーで返し、見出し 4〜6 は 3 に丸める。変換と語彙は React 非依存の `@plyrs/richtext` に置き、エディタ（ui）・Worker・DO が共有する。変換の忠実度はテストで固定する（19 件の往復）。
- **リンクの scheme（M4 のレビュー）**: リッチテキストの mark の `href` は validate-on-write（`buildRecordInputSchema`）で `http` / `https` / `mailto` / `tel` と scheme の無いもの（相対 URL・アンカー）だけを許し、ほかは `validation_failed` で拒否する（`packages/metamodel/src/link-href.ts`。WHATWG URL と同じく前後の制御文字・空白と中のタブ・改行を落としてから判定する）。Markdown 入力と JSON 入力の両方が同じ検証を通る。エージェントが書いた `javascript:` のリンクが公開され、利用者のフロントエンドで XSS になるのを防ぐ。tolerant read は使わないので、既に保存された値は読める（その record を次に書き込むときに直す必要がある）
- **信頼されないコンテンツ（論点 E1）**: record の本文は他の利用者が書いたデータなので、エージェントに指示として扱わせない。本文は `structuredContent` のデータ領域に置き、ツール説明でも明示する。本文中の指示に従った誤編集・誤公開は、この包み方・publish の既定オフ（16.8）・履歴からの復元（16.5）の 3 重で受ける。

### 16.11 初期リリースのツールとアセット（論点 D3）

初期リリースのツールは、型の参照（`type_list` / `type_get`、型スキーマは MCP の resources `plyrs://types/{key}` でも配る）、record の `list` / `search` / `get` / `create` / `update`（ブロック操作を含む）/ `delete`、`history` / `restore`、`publish` / `unpublish` / `compare`、アセット登録。型の変更・メンバー管理・モジュール有効化は後回し。

型とフィールドの `description` と、型単位の「執筆ガイド」欄（論点 A3、`writingGuide`、4000 文字以内）をメタモデルに足し、`type_get`・JSON Schema・resources・prompts に載せる（M2-8 で実装）。型をデータで持つ本システムでは、記事の構造と書き方を知る手がかりが型定義しかないため。配り方は 3 つ: `type_get` と resource `plyrs://types/{key}` の定義に `writingGuide` が載る。resource `plyrs://types/{key}/schema` は record の input の JSON Schema（`z.toJSONSchema`、フィールドの `description` と必須を含む。`application/schema+json`）。prompt `writing_guide`（引数 `type`）は型の説明・執筆ガイド・フィールドごとの型と必須と説明を 1 通にまとめる。執筆ガイドと型の説明は利用者が書いた設定なので、prompt の本文にも record と同じ前置き（16.10）を付ける。

アセットは、使い切りのアップロードトークンを返すツール + 既存の `POST /assets`（20MB 上限、assetGuard の beforeWrite）と、URL からの取り込みの 2 経路。R2 の Workers binding では署名付き URL を作れない。URL 取り込みは Worker から任意 URL を fetch するので、公開アドレスのみ許可・リダイレクト先の再検証・サイズ上限で SSRF を防ぐ。

### 16.12 公開の段階と限定公開

- **読み取り専用 MCP（M1）は preview と production の両方に出す**。production は **限定公開**とし、その意味は次の 3 つ: (1) 告知しない、(2) PAT を発行できるのはテナントの所有者だけ、(3) ツール名・返り値の形・PAT の形式は書き込み MCP の公開（M4）まで変えうる（後方互換の約束なし）。顧客がいないため露出が小さく、環境差（binding の env ごとの全定義、TanStack の SPA 配信）を早く踏める。
- **書き込み MCP（M4）は PAT 接続で公開し、OAuth（M3）の完成を待たない**。書き込みの安全性を担保するのは変更履歴・strict な競合判定・冪等な書き込み・publish の既定オフ（M2）であり、トークンの入手経路で DO 側の判定は変わらない。OAuth は後からホスト型クライアントの接続を足すものであり、M4 の前提ではない。

### 16.13 非目標と不採用

- **super 管理者向けの MCP**（dead-letters などの運用操作）は作らない。運営管理画面に閉じる。
- **Roots / Sampling / Logging** は Deprecated のため採用しない。運用ログは別の手段で取る。
- **公開側 MCP**（サイト訪問者向けに公開用 DB だけを読む読み取り専用 MCP、論点 D4）は管理用とは別のエンドポイント・別の認証として M5 で設計する。本章の対象外。
- **サービスアカウント**（人に紐づかない常駐エージェント、論点 C4）は D1 の `users` / `memberships` の変更を伴うため初期には採らない（未処理論点）。
