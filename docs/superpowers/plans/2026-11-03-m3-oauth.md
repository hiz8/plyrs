# M3 OAuth の認証基盤 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** claude.ai や ChatGPT のコネクタのように PAT を貼れないホスト型クライアントが、OAuth 2.1(認可コード + PKCE)で `https://<api>/mcp/t/:tenantId` に接続できる状態にする。登録は CIMD を優先し DCR を fallback に残す。同意画面で付与したスコープが PAT と同じ認可コンテキストに合流し、スコープ不足は `403 insufficient_scope` で step-up できる(ゲート G3)。

**Architecture:** 認可サーバーは `@cloudflare/workers-oauth-provider` v1 の分割 API(`OAuthAuthorizationServer`)を api Worker に置き、テナント別 issuer `${ADMIN_ORIGIN}/oauth/t/:tenantId`・単一 resource `${API_ORIGIN}/mcp/t/:tenantId` で**要求ごとに組み立てる**(決定 47)。admin は `/oauth` と `/.well-known/oauth-authorization-server` を api へ同一オリジン転送し、`/authorize` だけが admin オリジンのセッション cookie を見る。同意画面は api が HTML を描画する(M0-3 結果 4 節の案 i)。MCP の入口(`OAuthResourceServer`)の `validateToken` は PAT を接頭辞で振り分け、それ以外を同じ Worker 内の `OAuthAuthorizationServer.validateToken` に流し、両方を BLOCKLIST 経由で `McpAuth` に合流させる(決定 49)。グラントの props は `{userId, tenantId, role}` で、refresh のたびに `memberships` からロールを読み直す。

**Tech Stack:** `@cloudflare/workers-oauth-provider` 1.2.4(catalog 済み)、Hono 4(`hono/html` の自動エスケープで同意画面を描画)、Drizzle(D1)、`@cloudflare/vitest-plugin`、TanStack Router(admin の `/login` の `return_to`)、jsdom + Testing Library、Playwright。

**Spec:**

- `docs/superpowers/plans/2026-11-01-m0-3-oauth-spike-result.md`(試作コードは `origin/spike/mcp-oauth` の `apps/api/src/spike/mcp-auth-server.ts`・`mcp-gate.ts`、`apps/api/test/oauth-spike.test.ts`)
- `docs/superpowers/plans/2026-11-01-mcp-roadmap.md` 2 章 M3、3 章(M3-2 は M3-1、M3-3 は M1-3b・M1-5 に依存)、4 章(同意画面の実装形)、8 章(`/login` の `return_to`)

## Global Constraints

- **認可サーバーのオブジェクトは要求ごとに組み立てる**(構築 0.04 ms、M0-3 結果)。issuer と resource は URL と `vars` から決まる: issuer `${ADMIN_ORIGIN}/oauth/t/:tenantId`、resource `${API_ORIGIN}/mcp/t/:tenantId`。`API_ORIGIN` は api の `vars` に新設する(dev `http://localhost:5173`、preview `https://plyrs-api-preview.hiz.workers.dev`、production `https://plyrs-api.hiz.workers.dev`)。MCP の入口(M1-5)が要求の URL から作る resource と同じ値でなければ OAuth のトークンは audience 不一致で 401 になる
- **状態は `OAUTH_KV` だけ**(ライブラリ固定名の KV binding)。wrangler.jsonc のトップレベル・preview・production の 3 か所に定義する。preview / production の実 ID は所有者が `wrangler kv namespace create` で作って転記する(`docs/deploy.md` 1 節に足す)。**実 ID が入るまで M3-1 を main にマージしない**(main への push は preview に自動デプロイされる)
- **CIMD には `compatibility_flags: ["global_fetch_strictly_public"]`** が要る(トップレベルに置く。`compatibility_flags` は env に継承される。`wrangler deploy --dry-run --env preview` で確かめる)。DCR は `clientRegistrationEndpoint` を `${issuer}/oauth/register` に設定して残す
- **access token の TTL は 15 分(`accessTokenTTL: 900`)、refresh token はライブラリ既定の 30 日**。ロールは同意時に props へ入れ、refresh のたびに `memberships` から読み直す(`tokenExchangeCallback`)。会員でなくなっていれば `invalid_grant` でグラントごと失効させる
- **スコープに階層は設けない**(16.3)。スコープ名は `auth/pat.ts` の `PAT_SCOPES` と同じ(`record:read` `record:write` `record:delete` `record:publish` `type:manage`)。認可サーバーの `scopesSupported` もこれ。実効権限 = スコープ ∩ ロールの判定は DO の `invoke`(M1-1)のまま
- **publish の既定(論点 C5)**: 同意画面で `record:publish` は既定で外し、所有者にだけ選択肢を出す。付与できるスコープはロールごとに `allowedScopes(role)`(`auth/pat.ts`。PAT の発行と同じ規則)に限る
- **会員でなければ同意に進ませない。** `/authorize` は (1) `parseAuthRequest`、(2) セッション cookie(無ければ `/login?return_to=…` へ 302)、(3) BLOCKLIST(`blocked:user` / `blocked:membership`)、(4) `memberships` の現在のロール(無ければ 403 の HTML)、の順
- **同意画面に出す文字列はすべてクライアント由来を疑い、エスケープする**(`clientName` `clientDomain` `redirectHost` `scope`)。`hono/html` のテンプレートで補間し、`raw()` は使わない
- **`/login` の `return_to` は同一オリジンの `/oauth/t/` 配下のパスだけ許可する**(先頭が `/oauth/t/`、`//` やスキームを含まない)。許可外は無視して従来どおり `/tenants` へ
- **エラーの 3 層(16.7)**: スコープ不足は MCP の入口で `insufficientScope()`(`403` + `WWW-Authenticate: Bearer error="insufficient_scope", scope="…"`)。DO の `invoke` の `insufficient_scope` は防御として残す(入口を通らない呼び出し向け)
- **OAuth の `tokenId` はグラント ID**(失効の単位。16.3)。ライブラリのトークンは `userId:grantId:secret` の形(`docs/resource-servers.md`)なので 2 つ目の要素を使い、`validateToken` が返す `userId` と 1 つ目の要素が一致することを確かめる
- **認可サーバーのエラーは `onError` で `internal.category` / `internal.reason` を `console.warn` に出す**(トークンや本文は出さない)
- DO の RPC 戻り値は `src/rpc-unwrap.ts` の `asXxx()` で実型へ戻す。`@ts-expect-error` は使わない
- コメント・ドキュメント・コミットメッセージ・画面の文言は日本語、用語は `docs/glossary.md`(「スコープ」「PAT」「トークンの種別(tokenKind)」)に従う。コミットは各タスクの最後に 1 つ
- PR は M1・M2 と同じスタック(各タスクが前のタスクを base にする)。ブランチは `claude/project-thread-fb4bgr-m3-<番号>`、計画 PR は `claude/project-thread-fb4bgr`

## Review Focus

1. **別テナントの OAuth トークン**: テナント A の issuer で得た access token を `/mcp/t/<B>` に出すと 401 になること。resource(audience)が `/mcp/t/<A>` に束縛され、B の認可サーバーは `resources` に A を持たないため(Task 3 のテスト)
2. **同意画面の権限昇格**: 編集者が `record:publish` や `type:manage` をフォームに足して POST しても付与されないこと(POST 側でも `allowedScopes(role)` で絞る。Task 2)
3. **会員を外された人の refresh**: 同意後に `memberships` から消された利用者の refresh が `invalid_grant` になり、以後その refresh token で access token が得られないこと(Task 4)
4. **ログイン往復の open redirect**: `/login?return_to=https://evil.example/` や `//evil.example` や `/tenants` では `/tenants` へ行くこと(Task 2 の admin テスト)
5. **PAT の挙動を変えないこと**: M3-3 の合流後も PAT の 401 / 403 / レート制限のキー(`mcp-route.test.ts` 既存)が全部通ること。接頭辞が `plyrs_pat_` のトークンは OAuth 側の `validateToken` に渡らないこと(Task 3)
