# M4 書き込み MCP の公開 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** エージェントが PAT(と M3 の OAuth)で、record の作成・ブロック単位の編集・削除・履歴からの復元・公開と取り下げ・アセットの登録を MCP から行える状態にし、ゲート G4(書き込み・競合・スコープ不足の E2E、/security-review の指摘の解消、ツールごとの DO 計測が基準内)を満たす。

**Architecture:** M2 でカタログに移した書き込み操作(`ops/write.ts`・`ops/history.ts`)の `via` に `"mcp"` を足して `tools/list` に出す。DO 側の処理は増やさず、リッチテキストの Markdown 入力とブロック操作は DO の操作ハンドラの手前(`ops/richtext-input.ts`)で ProseMirror JSON に解決してから既存の `resolveSyncWrite`(strict)と `writeRecordCore` に流す。publish の確認は MRTR の elicitation(`inputRequired` + HMAC の `requestState`)で Worker 層(`mcp/server.ts`)が行う。アセットは「DO に使い切りのアップロードトークンを置き、api オリジンの `POST /mcp/t/:tenantId/uploads/:token` で受ける」経路と、「Worker が SSRF 対策付きで URL を取りに行く」経路の 2 つで、どちらも既存の `POST /assets` と同じ保存関数を通す。各 `invoke` は DO-SQLite の rows read / written を数えて返し、Worker がツール単位で構造化ログに出す。

**Tech Stack:** `@modelcontextprotocol/server` 2.4.0(`inputRequired` / `acceptedContent` / `createRequestStateCodec`)、`@plyrs/richtext`(`markdownToRichText` / `richTextToMarkdown`)、Drizzle(DO-SQLite のマイグレーション 1 本)、Hono、`@cloudflare/vitest-plugin`、Playwright、wrangler 4(`deploy --dry-run` / `dev --no-bundle`)。

**Spec:**
- `docs/design-spec.md` 16.4(カタログ)、16.5(履歴)、16.6(strict・`attempt`)、16.7(冪等・エラーの 3 層)、16.8(publish の確認)、16.10(Markdown・ブロック ID・E1)、16.11(初期リリースのツールとアセット)、16.12
- `docs/superpowers/plans/2026-11-01-mcp-roadmap.md` 2 章 M4、4 章(未決事項)、9 章・10 章(M2・M3 の申し送り)
- SDK の型: `node_modules/@modelcontextprotocol/server/dist/index.d.mts`(`inputRequired`・`acceptedContent`・`inputResponse`・`createRequestStateCodec`・`ServerOptions.requestState`)

## Global Constraints

- **既存経路を通す**: 書き込みは `writeRecordCore`、公開は `publishRecordCore` / `unpublishRecordCore`、削除は `deleteRecordCore`、復元は `restoreRecordCore`、アセットは `createAssetRecord` RPC。MCP 専用の書き込み処理を DO に作らない
- **エージェント経路は strict**(決定 42、`conflictModeFor("mcp")`)。`status` を変える更新は現在の `fieldVersions` 全体との一致を要求する(既存の実装をそのまま使う)
- **再適用は 2 回まで**(16.6)。`record_update` に `attempt: z.number().int().min(1).max(3).default(1)` を足す。`attempt >= 3` で conflict なら `details.giveUp: true` と「人に回す」文を返す
- **リッチテキストの入力は 3 形**: ProseMirror のエンベロープ(従来)、Markdown 文字列(全置換)、`{ blocks: BlockOp[] }`(`record_update` のみ。最上位ブロックの `id` で指す部分編集)。変換後は必ず `checkRichText` を通し、語彙外は `unsupported_markdown`
- **publish / unpublish の確認(16.8)**: クライアントが `elicitation` を宣言していれば MRTR の form elicitation で確認する。宣言していなければ**拒否して人に回す**(業務エラー `confirmation_unavailable`。所有者の判断カードの結果で変わりうる。Task 5 の Step 0)。`requestState` は `createRequestStateCodec` で HMAC 保護し、bind は `${tenantId}:${userId}:${tokenId}`、TTL は 300 秒、payload は `{ op, recordId }`。鍵は `JWT_SECRET` から HMAC-SHA256(`"plyrs:mcp-request-state:v1"`)で導出する(新しい secret を足さない)
- **publish ツールは常に `tools/list` に出し**、スコープ不足は入口の `403 insufficient_scope`(M3-3 の既存経路)。ツール説明に「PAT 接続では所有者が `record:publish` 付きの PAT を発行する」を書く(ロードマップ 4 章の仮置きを採用)
- **アップロードトークン**: 32 バイトの乱数を base64url にした文字列、DO には SHA-256 だけを置く。TTL 600 秒、使い切り(DO 内で `used_at` を立ててから R2 に書く)、上限 20 MiB(既存の `MAX_ASSET_SIZE_BYTES`)。発行した利用者・ロール・tokenId を行に持ち、受け取り時に BLOCKLIST の 2 キーを照会する
- **URL 取り込みの SSRF 対策**: `https:` のみ、ポートは既定(443)のみ、ホストが IP リテラルなら拒否(私的・ループバック・リンクローカルを個別に判定しない。全部拒否)、`localhost` と `.localhost` `.local` `.internal` で終わる名前は拒否、`redirect: "manual"` で最大 3 回、各ホップで同じ検査、`AbortSignal.timeout(10_000)`、本文は読みながら 20 MiB で打ち切り、Content-Type は `image/png` `image/jpeg` `image/gif` `image/webp` `image/avif` のみ(SVG は不可)。実行時は `global_fetch_strictly_public`(M3-1 で有効化済み)が二重の防御になる
- **エラーの 3 層(16.7)**: 業務エラーは `isError: true` で `structuredContent.error = { code, message, details? }`(**`details` を落とさない**。現状の `failure()` は落としている)
- **本文の包み方(E1)**: 書き込みツールの結果の text も `UNTRUSTED_PREFACE` で始める
- **DO の計測**: `invoke` ごとに rows read / written を合計し `InvokeResult.meter = { rowsRead, rowsWritten }` で返す。Worker は `console.log(JSON.stringify({ event: "mcp.op", tenantId, op, ok, code?, rowsRead, rowsWritten, ms }))`(トークン・本文・利用者 ID は出さない)
- DO の RPC 戻り値は `rpc-unwrap.ts` の `asXxx()` で戻す。`@ts-expect-error` は禁止。マイグレーションは `pnpm --filter @plyrs/db generate` で生成し手書きしない
- コメント・ドキュメント・コミットメッセージ・ツール説明は日本語、用語は `docs/glossary.md` に従う。コミットは各タスクの最後に 1 つ
- PR は M2・M3 と同じスタック。計画 PR は `claude/project-thread-lb5o1r`、各タスクは `claude/project-thread-lb5o1r-m4-<番号>`(前のタスクを base にする)

## Review Focus

1. **ブロック操作の ID が古い**: エージェントが `record_get` で見た後に人がその段落を消した場合、`blocks` の `replace` は `block_not_found` ではなく(同じフィールドの版が進んでいるので)`conflict` を返すこと。版の検査がブロックの解決より先(Task 2)
2. **elicitation の requestState の流用**: 利用者 A の確認で得た `requestState` を、別のトークン・別の recordId の publish に付けて再送しても公開されないこと(bind と payload の照合。Task 5)
3. **アップロードトークンの二重使用と横取り**: 同じトークンで 2 回 POST すると 2 回目は 410、別テナントの URL に同じトークンを出すと 404、BAN された利用者のトークンは 403(Task 7)
4. **URL 取り込みのリダイレクト**: 公開ホストから `http://169.254.169.254/` や `https://10.0.0.1/` へ 302 する URL を渡すと、取りに行かずに `url_not_allowed` を返すこと(Task 8)
5. **書き込み 1 回の rows read が record 数に比例しない**: 10 件と 300 件のテナントで `record_update` / `record_create` / `record_delete` / `record_publish` の rows read が一致する(差は 0。Task 9)
