# M5b 旧版プロトコルのクライアントへの対応を決める

**Goal:** ロードマップ 4 章の未決事項「旧版プロトコルのクライアントへの対応」(2025 年版の `initialize` から始めるクライアントに何を返すか)を決める。

**結論(決定 56、所有者の判断、2026-11-07):** 仕様 2026-07-28 のみを受け、2025 年版は従来どおり `-32022` で拒否する。JSON-RPC のバッチは入口で拒否する。ChatGPT への対応が必要になったら再検討する。

## 経緯

1. M5a の確認(2026-11-07)で、MCP Inspector と SDK v2 のクライアントの既定が 2025 年版で、そのままでは接続できないと分かった
2. 2025 年版を SDK の `createMcpHandler` の `legacy: "stateless"` で受ける実装を作り、PR #94 で検証した(api のテスト 800 件、E2E 全 8 spec が通過)。試作で 2 つの穴を見つけて塞いだ
   - SDK の 2025 年版の経路は JSON-RPC バッチを受け、配列の中の `tools/call` が入口のスコープ判定と Rate Limiting のキーを素通りした
   - 2026-07-28 で得た確認の `requestState` と承諾を 2025 年版の要求に付け替えると、確認のフォームを経ずに公開まで進んだ
3. 所有者が、実装の複雑度・セキュリティ・未来志向の 3 点を懸念した。CMS の利用者はエディタ(VS Code・Cursor)ではなく、claude.ai や Claude デスクトップアプリなどの汎用アプリから接続すると見込む
4. claude.ai は G3(2026-11-03)で 2026-07-28 だけを受ける入口に接続できていた。対象を汎用アプリに絞ると 2025 年版を受ける必要は小さく、受けると SDK の別の経路が攻撃面に加わり、その接続では publish の確認も出せない。#94 は閉じ、受けない方針にした
